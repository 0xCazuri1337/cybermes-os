## How it works

- **Stored XSS requires the payload to persist in a server-side store and later render in another user's response, so proof needs two distinct steps.**
  - kills it if: The payload executes only in the submitting user's own session and never renders for any other user or role.
  - `xss.prereq.stored.two_step_store_then_second_user_view`

## Test

- **Stored XSS is proven only by storing a payload as one identity and loading the exit point as a second identity, because your own session re-rendering your own input proves storage and reflection, never cross-user execution.**
  - kills it if: The procedure is wrong if you only ever test with one account and the app renders stored values differently per role - the marker may be HTML-encoded for the author and injected raw into an admin moderation queue, so your own view can look safe while the privileged view is exploitable. It is also wrong where stored data is overwritten before any second read (recent-searches lists, ephemeral carts); a marker found once is not proof of durable storage - re-read the exit point after an unrelated action to confirm it survives.
  - `xss.test.stored.two_identity_entry_to_exit_point_link`

## Reject before you report

_Each bullet is a rejection rule — the observation that KILLS the candidate._

- **Reject a stored XSS candidate when the submitted payload never appears in any response served to another user or role, because a store-only write with no second-user render is not cross-site script execution.**
  - kills it if: The rule is wrong if any second surface renders the stored value - an admin moderation queue, a different user's listing or profile page, a notification email, an export/CSV/PDF generator, a webhook payload or a third-party integration that re-renders the string as HTML. Any one of those makes it genuine stored XSS, because the hunter now has two distinct steps: store, then a second user's response executes it.
  - `xss.fp_rule.stored_xss.entry_point_never_reaches_second_user_view`

## Chaining

_Each bullet is a step in escalating script execution into impact._

- **A stored payload submitted through a low-privilege account that later renders inside an administrator's session escalates a self-XSS into administrator compromise, and proving it requires two distinct identities.**
  - kills it if: If the payload fires only in the submitting account's own session and never renders in a second, higher-privileged user's view, then it is self-XSS and the escalation step is unproven.
  - `xss.chain_link.stored_payload_reaching_an_administrator_view`

## Applies to every XSS sub-type

_False-positive rules, validation bars and escalation steps that are not specific to this delivery type. Canonical copies live in `classes/xss.md` and `skills/xss-hunting/SKILL.md`; they are listed here so this file can be used on its own._

- **A CSP only blocks inline or foreign script execution; nonces, hashes and strict-dynamic decide whether an injected payload can still run.**
  - kills it if: The policy is nonce- or hash-based with an unguessable per-load nonce and no unsafe-inline, and the payload yields no element carrying a matching nonce or hash.
  - `xss.bypass.csp_nonce_hash_or_strict_dynamic_gap`
- **HTML-encoding characters the filter blocks defeats it inside an event-handler attribute, because the browser HTML-decodes attribute values before JavaScript runs.**
  - kills it if: This is wrong if the browser decodes the attribute only once and the application re-encodes after decoding, or if the sink is textContent or a DOM property that receives the still-encoded value without HTML decoding.
  - `xss.bypass.filter.html_entity_decoding_of_attribute_values`
- **A filter blocking parentheses is bypassed by invoking the function without them, for example with a throw statement and a global exception handler.**
  - kills it if: This is wrong if the filter also blocks the throw keyword, the semicolon, or the equals sign, or if the application CSP forbids inline handlers so no assignment is ever reached.
  - `xss.bypass.filter.parentheses_free_invocation`
- **A nonce-based CSP only blocks injected inline script, so DOM sinks and dangling markup remain exploitable under the same policy.**
  - kills it if: This is wrong if the policy is nonce- or hash-based with an unguessable per-load nonce and the payload yields no element carrying a matching nonce or hash AND no other reachable sink exists.
  - `xss.bypass.trusted_types.dom_sink_requires_policy`
- **HttpOnly and SameSite cookie attributes block cookie exfiltration and cross-site request delivery but do not stop same-origin injected script from acting through the victim's session, so a hardened cookie posture is not an XSS mitigation.**
  - kills it if: If the same-origin request is sent without the session cookie while an identical hand-crafted request from the same origin does carry it, the cookie is being withheld for a reason other than SameSite and the claim does not describe this target.
  - `xss.chain_link.cookie_posture.httponly_and_samesite_do_not_block_same_origin_script`
- **An anti-CSRF token provides no protection against XSS, because script executing in the victim's origin can read the token out of the page or the response and replay the state-changing request with it.**
  - kills it if: If the state-changing request is refused with a token-validation error even when the script supplies the token read from the same page, the defence is holding and this chain link does not apply to that endpoint.
  - `xss.chain_link.csrf_token_read_defeats_csrf_defence`
- **Changing the account email address from injected script and then triggering the normal password-reset flow yields full account takeover without ever stealing a session cookie.**
  - kills it if: If the email-change endpoint re-authenticates the user or re-sends the current password before it will change the address, or if the reset mail still goes only to the original address, the takeover step fails and this chain link does not apply.
  - `xss.chain_link.email_change_then_password_reset_takes_over_account`
- **Client-side prototype pollution chains into DOM XSS when a polluted prototype property is later consumed as an unsafe sink value.**
  - kills it if: The merge routine rejects or ignores __proto__ and constructor keys, or no sink reads any property an attacker can pollute on Object.prototype.
  - `xss.chain_link.prototype_pollution_to_dom_xss`
- **Once injected script executes in the victim's origin it inherits every action the victim's authenticated session can perform, so the impact ceiling is the victim's own account authority rather than a popup.**
  - kills it if: If the same-origin request made from the injected script is rejected as unauthenticated, or returns the same body as an anonymous session, then the script is not running with the victim's session authority and the claim's ceiling does not apply to that finding.
  - `xss.chain_link.same_origin_authority.victim_session_actions`
- **A stored payload submitted through a low-privilege account that later renders inside an administrator's session escalates a self-XSS into administrator compromise, and proving it requires two distinct identities.**
  - kills it if: If the payload fires only in the submitting account's own session and never renders in a second, higher-privileged user's view, then it is self-XSS and the escalation step is unproven.
  - `xss.chain_link.stored_payload_reaching_an_administrator_view`
- **When a site reflects attacker input into its own Content-Security-Policy - typically the trailing report-uri directive - a semicolon lets the attacker append directives, and the script-src-elem directive lets an appended script-src overwrite the existing nonce or hash based script-src entirely.**
  - kills it if: The claim is wrong if the site does not reflect any input into the policy, since there is then nothing to inject and the nonce stands. It is also wrong if the reflected value is filtered so a semicolon or a comma cannot appear, because then no new directive can be opened. It is wrong for browsers that do not implement script-src-elem, where an appended script-src would simply be dropped as a duplicate and the original policy would still apply. And it is wrong for servers that deliver the policy as a meta tag rather than a header in a context where the attacker controls only part of the value, since the injected text is then inert element content rather than a directive.
  - `xss.evidence.csp.script_src_elem_overwrite_defeats_nonce_policy`
- **Reject a report's 'steals session cookies' impact claim when the session cookie carries the HttpOnly attribute, and restate the impact as in-origin action on behalf of the victim instead.**
  - kills it if: The rule is wrong if the session cookie lacks HttpOnly and document.cookie returns it to injected script, in which case full session replay IS achievable and the original impact claim stands. It is also wrong when the sensitive credential is not the cookie at all - a JWT or API token in localStorage or sessionStorage, or a CSRF token readable from the DOM, is unaffected by HttpOnly. Read the Session Management cheat sheet's own warning before assuming HttpOnly helps: it only protects the confidentiality of that one cookie.
  - `xss.fp_rule.cookie_impact.httponly_cookie_defeats_exfiltration_chain`
- **Reject a DOM or reflected XSS candidate when the live page ships a CSP whose script-src carries a nonce or hash source without unsafe-inline and without strict-dynamic, because your injected inline script and inline event handlers cannot execute.**
  - kills it if: The rule is wrong when the policy contains 'unsafe-inline' (or 'unsafe-eval' for eval-style payloads), or when strict-dynamic is present and the injection point runs on a page that already loaded a nonced/hash-trusted script - in both cases a nonce-less injected script is executed anyway and the finding is a full XSS. It is also wrong if the CSP is only a report-only header (Content-Security-Policy-Report-Only), which logs violations without blocking anything.
  - `xss.fp_rule.csp.live_nonce_or_hash_policy_blocks_payload`
- **Reject a DOM clobbering or prototype-pollution XSS candidate when the clobbered or polluted property is only read as a string into textContent, an attribute or a URL fetch, and never reaches an HTML parser or script-execution context.**
  - kills it if: The rule is wrong if the clobbered or polluted property is later assigned into an HTML-executing sink - a clobbered script src/iframe src whose value navigates to attacker markup, or a polluted property consumed by a template that renders it as HTML - because that is script execution with an injection-only primitive, and it is a real XSS. OWASP's own note that CSP mitigates clobbering of script sources but not already-present code that can be abused for execution is the same distinction seen from the mitigation side.
  - `xss.fp_rule.dom_clobbering.property_read_into_safe_sink`
- **Reject a reflected XSS candidate when the reflected value appears in the response only as HTML entities or percent/unicode escapes that the browser decodes back to inert text in that context, because encoding is what makes the reflection non-exploitable.**
  - kills it if: The rule is wrong if the encoding is applied for the wrong context - for example only HTML-entity-encoded output dropped inside a JavaScript string, a URL, a CSS value or an unquoted attribute, where &quot; and &#39; do not neutralise a quote delimiter and a ';alert(1)// payload still breaks the string. It is also wrong if the entity is decoded and re-serialised anywhere before rendering (a client-side read of .innerHTML followed by a re-write, or a client-side template that re-interprets the text as HTML), because then the inert text becomes live markup.
  - `xss.fp_rule.html_encoding.entity_encoded_reflection_cannot_break_context`
- **Reject a JSON API endpoint reported as XSS when the response Content-Type is application/json and no client-side code path inserts the reflected value into an HTML document.**
  - kills it if: The rule is wrong if the same reflected value reaches an HTML-executing context through any code path: the API is called by a front end that assigns the response into innerHTML or a framework's raw-HTML binding, the endpoint is reachable at the same path with a text/html or JSONP callback content type, or the server renders the stored value into an HTML page for other users. Then the JSON body is only the delivery mechanism, and the finding is a genuine XSS located at the sink.
  - `xss.fp_rule.json_api.content_type_json_is_not_html_execution`
- **Reject a prototype-pollution finding reported as XSS unless the polluted property value is read back and written into an HTML-executing sink, because polluting Object.prototype alone executes no script in any page.**
  - kills it if: The rule is wrong if the polluted property is consumed by a templating engine or a client-side render that inserts it as markup - a server-side template interpolating the inherited property, or front-end code writing it to innerHTML or a raw-HTML framework binding - because then the pollution is the injection primitive and the result is stored XSS reachable by every user of the app. Equally, if the pollution reaches a code-execution gadget (a template engine option object, a child-process invocation), that is RCE, which is a stronger finding than the XSS report claimed.
  - `xss.fp_rule.prototype_pollution.property_write_is_not_html_injection`
- **A reflected XSS on an anonymous, read-only page is not automatically informational; it still executes script in every visitor's origin.**
  - kills it if: The page's origin exposes no authenticated state, no same-origin privileged endpoints and no tokens reachable from injected script, leaving only a bare popup.
  - `xss.fp_rule.readonly_brochureware_page_does_not_clear_xss`
- **Reject a sanitizer-bypass XSS claim when the rendered page shows the payload as inert text with the dangerous markup stripped, because a payload that does not become live DOM in the browser is not a bypass.**
  - kills it if: The rule is wrong if a real element with a live event handler or a navigable javascript:/data: URL is present in the rendered DOM and your callback endpoint receives the request - that is a genuine sanitizer bypass and a real XSS, even if the sanitizer appeared to strip <script>. The rule also does not apply where the string is sanitized and then mutated or re-serialised before insertion, since the protection can be voided downstream; check the sink, not the sanitizer call.
  - `xss.fp_rule.sanitizer.output_observed_inert_in_page`
- **Reject an XSS candidate as unproven when the payload can only be made to render by pasting attacker-supplied JavaScript into the submitter's own address bar or console, because that is self-XSS and not a cross-user finding.**
  - kills it if: The candidate stops being self-XSS the moment a working delivery exists: a crafted URL (or a CSRF-style auto-submitting form) that fires the payload automatically in any other user's browser, on a page an authenticated victim visits. Then it is ordinary reflected XSS and this rejection rule is wrong. Equally, if the 'pasting' step is not required because the value is stored and later rendered to other users, the finding is stored XSS, not self-XSS.
  - `xss.fp_rule.self_xss.payload_renders_only_in_submitter_browser`
- **Reject a DOM-based XSS candidate when the traced attacker-controlled source only ever reaches textContent, innerText, or setAttribute with a hardcoded non-event attribute, because those sinks treat the value as text and never parse it as markup.**
  - kills it if: The candidate is a real DOM XSS if the identical tainted value, in the identical code path, is also passed to an execution-capable sink - innerHTML/outerHTML/insertAdjacentHTML/document.write/eval/string setTimeout - anywhere the same value can reach on another page load, in a fallback branch, or for a different input shape. This rule is also wrong if setAttribute's attribute NAME is derived from the same tainted input (setAttribute(t, v) where t is user-influenced), because OWASP limits setAttribute's safety to hardcoded, innocuous attribute names; an injected name such as onmouseover re-creates an injection sink.
  - `xss.fp_rule.sink_reachability.source_never_reaches_execution_sink`
- **Reject a stored XSS candidate when the submitted payload never appears in any response served to another user or role, because a store-only write with no second-user render is not cross-site script execution.**
  - kills it if: The rule is wrong if any second surface renders the stored value - an admin moderation queue, a different user's listing or profile page, a notification email, an export/CSV/PDF generator, a webhook payload or a third-party integration that re-renders the string as HTML. Any one of those makes it genuine stored XSS, because the hunter now has two distinct steps: store, then a second user's response executes it.
  - `xss.fp_rule.stored_xss.entry_point_never_reaches_second_user_view`
- **Serving the vulnerable page over HTTPS changes nothing about the attack, because same-origin script execution is scoped by origin, and https is part of the origin definition rather than a barrier to it.**
  - kills it if: If the payload only executes on a plaintext HTTP origin and the browser blocks it or the application serves different content over HTTPS, then the scheme does affect the finding and this claim does not hold for it.
  - `xss.impact.transport_security.tls_does_not_mitigate_same_origin_execution`
- **A JSON response served as text/html and interpolated into a page becomes an HTML injection point even though the body is JSON.**
  - kills it if: The endpoint returns application/json and no code path inserts the response body into an HTML document, so injected markup is never parsed as markup.
  - `xss.technique.json_response.embedded_into_html_document`
- **Before writing an impact claim, read the live response headers for the CSP nonce/hash/strict-dynamic directives, the HttpOnly flag on the session cookie, and any require-trusted-types-for directive, because each one caps what your confirmed execution can actually do.**
  - kills it if: The procedure is wrong if you treat a nonce you observed on one page load as a permanent value and paste it into a payload - a nonce is regenerated per response, so a captured nonce will not match and the test fails for the wrong reason. It is also wrong to conclude a control blocks impact from the header alone: nonce/hash/strict-dynamic govern script execution, not already-confirmed event-handler execution through a parsed HTML node in every policy, and HttpOnly says nothing about tokens held in localStorage.
  - `xss.test.controls.verify_csp_httponly_trusted_types_before_impact`
- **An escape routine that is correct for one context does not protect another, so a finding is wrong until the encoding is shown to match the exact context the value lands in.**
  - kills it if: This is wrong if the value is context-correctly encoded by a vetted encoder for its exact destination, or if it is inserted as a property value on a sink that encodes automatically.
  - `xss.validation.encoding_must_match_landing_context`
- **An HttpOnly session cookie removes the cookie-exfiltration chain, so impact must be restated as in-origin actions rather than session theft.**
  - kills it if: The session cookie lacks HttpOnly and document.cookie returns it inside the injected script, so full session replay is achievable.
  - `xss.validation.httponly_blocks_cookie_theft_chain`
- **A payload that fires an alert only in the hunter's own browser demonstrates script execution but not a reportable vulnerability, because impact requires the payload to reach another user's session or a reachable victim path.**
  - kills it if: If the payload demonstrably renders and executes in a second, independently authenticated session or in a view reached by another user, then the marker is not self-only and the finding does clear the bar.
  - `xss.validation.self_fired_marker_is_not_a_reportable_finding`
