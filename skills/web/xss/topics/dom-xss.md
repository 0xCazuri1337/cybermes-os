## Where to look

- **DOM XSS exists only where an attacker-controllable source reaches an execution-capable sink; reading the source alone is not a finding.**
  - kills it if: The source is read but the value always flows into a safe sink such as textContent or setAttribute, or never reaches any execution-capable sink.
  - `xss.signal.dom.executable_source_to_sink_path`

## Technique

- **An injected unclosed attribute makes the browser send the rest of the response to an attacker URL, achieving data capture with no script execution.**
  - kills it if: This is wrong if the application escapes or filters the quote and angle-bracket characters that the breakout requires, or if no sensitive data follows the injection point in the response.
  - `xss.technique.dangling_markup.exfiltrates_without_script_execution`
- **An innerHTML sink will not execute an injected script element, so execution requires an event-handler element such as img or iframe.**
  - kills it if: This is wrong if the sink is document.write rather than innerHTML, if the browser is one that still runs script elements assigned via innerHTML, or if a separate code path appends the node and executes it.
  - `xss.technique.dom.innerhtml_rejects_script_use_event_handlers`
- **document.write, innerHTML, outerHTML, insertAdjacentHTML and jQuery html() are execution-capable sinks, while textContent is not.**
  - kills it if: This is wrong if the value reaching the sink is sanitised by a vetted library configured for that sink, or is only ever assigned as a property value that the browser does not parse as markup.
  - `xss.technique.dom.sink_list_execution_capable`
- **DOM-based XSS exists only where an attacker-controllable source reaches a sink that supports dynamic code execution.**
  - kills it if: This is wrong if the source is read but its value only ever reaches a safe sink such as textContent or setAttribute, or never reaches any execution-capable sink.
  - `xss.technique.dom.source_to_execution_sink`
- **The URL is the most common DOM XSS source, and the payload can ride in the query string, the fragment, or the path.**
  - kills it if: This is wrong if the application reads the location and immediately decodes or strips it before any use, or if the page never passes the value into a sink that renders or executes it.
  - `xss.technique.dom.url_fragment_and_query_as_source`
- **Injected markup with an id or name attribute creates a window/document property that shadows built-in APIs, turning attacker markup into a live configuration object.**
  - kills it if: This is wrong if the page never reads the clobbered property, if the injected markup cannot set an id or name attribute in that position, or if the code uses getElementById or a scoped lookup that bypasses named property access.
  - `xss.technique.dom_clobbering.named_element_shadows_configuration_object`

## Test

- **When a filter blocks your quote or tag characters, probe the decoder gap in a fixed order - HTML-entity-encode the blocked character first, then prepend a backslash to neutralise the app's own escaping - and a hit proves the filter normalises but does not neutralise.**
  - kills it if: The procedure is wrong if the entity probe is fired at the wrong layer: &#39; only helps where the browser HTML-decodes before parsing, so sending it into a JS string inside a <script> block, into a URL, or into a CSS value does nothing, and a hunter who treats a non-firing entity probe as proof of safety has only tested one decoder. It is also wrong to stop at the first working bypass - the same filter may have a second gap, and reporting only the first understates the defect.
  - `xss.test.bypass.entity_backslash_probe_sequence`
- **When a filter blocks parentheses you switch to a parentheses-free invocation, and when the reflection lands inside backticks you use ${...} with no terminator at all - both are determined by what step 1 showed you in the response.**
  - kills it if: The procedure is wrong if the marker lands in a template literal that is never actually evaluated as a tagged/interpolated expression at runtime (a string built for display, or a literal inside a JSON blob parsed as data) - ${...} then stays literal text and you will have burned the window on the wrong technique. It is also wrong to assume parentheses-free invocation survives everywhere: onerror=alert;throw 1 needs an element that fires error, so on a non-error context the payload is inert and the miss is a context error, not proof the filter holds.
  - `xss.test.bypass.parens_free_and_template_literal_probes`
- **Grepping a downloaded JS bundle for the concrete sink token set - innerHTML, outerHTML, insertAdjacentHTML, document.write/writeln, eval, new Function, setTimeout/setInterval with a string first argument, and the jQuery html/append family - is what converts 'this page uses innerHTML somewhere' into a list of lines you can actually test.**
  - kills it if: The procedure is wrong if the sink token appears in dead code, a comment, a minifier artifact, or an error-handling branch that never runs - a raw grep hit is a candidate list, not a vulnerability, and a hit list with no reachability analysis will generate false positives. It is also wrong as a completeness claim: many apps reach sinks through a framework abstraction (a template engine's {{{ }}} escape, a v-html directive, React's dangerouslySetInnerHTML) where the literal token never appears in any bundle.
  - `xss.test.dom.enumerate_dangerous_sinks_in_bundle`
- **For DOM XSS you must seed the marker into a client-side source such as location.search and locate it in the live DOM with devtools Control+F, because the browser's View Source never shows JavaScript-injected nodes.**
  - kills it if: The procedure is wrong if the app renders the marker only after an interaction or a timer - a click, a scroll, a setTimeout, a route change - because a single load-time Control+F finds nothing and the source IS reachable. It is also wrong where the value is passed to an execution sink such as eval or setTimeout-with-string, where the marker legitimately never appears in the DOM, so 'absent from the DOM' is not evidence of safety and must not be recorded as a clean result.
  - `xss.test.dom.html_sink_marker_via_devtools_control_f`
- **A DOM XSS claim is only proven when the debugger shows an actual value flowing from a source read into an execution sink, because grepping source and sink names separately proves nothing about the path between them.**
  - kills it if: The procedure is wrong if the path is data-dependent and your single marker run takes a different branch than the attacker's input would (a length check, an if/else on the first character, a try/catch). A clean debugger trace on one marker does not prove the branch an attacker's payload would take is also safe. It is also wrong to stop at the first sink: a value often flows into a safe sink AND an unsafe sink, so the trace must continue to every use of the tainted variable.
  - `xss.test.dom.prove_source_to_sink_path_with_debugger`

## Validation bar

_Each bullet states what must be true before this is a finding._

- **A page that handles postMessage without validating event.origin accepts attacker-controlled input from any origin.**
  - kills it if: This is wrong if the handler verifies event.origin against an exact expected origin before acting, or if the data is only used in a context that cannot reach a sink or a privileged action.
  - `xss.technique.postmessage.receiver_must_validate_event_origin`
- **If a DOM source value is URL-encoded before reaching the sink the markup payload cannot survive, making the candidate a false positive.**
  - kills it if: A non-encoded payload with no percent sequences in the traced value reaches the sink and executes script in the victim's browser.
  - `xss.validation.dom.url_encoded_source_kills_payload`

## Evidence

- **Injecting an unterminated img src attribute captures the rest of the victim's response into an outbound request URL without executing any script, because the HTML tokenizer stays in the double-quoted attribute value state until it finds the next quotation mark anywhere in the document.**
  - kills it if: The claim is wrong if the surrounding markup contains no double quotation mark at all after the injection point, because the attribute value then consumes to end of file and the browser issues a request with an empty or truncated value. It is also wrong on Chrome, which blocks img URLs containing raw angle brackets and newlines, since the captured content would have to contain one of those to be interesting. It is wrong if the site filters '>' or the quotation mark in the landing context, since the attacker cannot open the new tag at all. And it is wrong under a CSP with img-src 'self', which blocks the external request entirely, leaving no capture.
  - `xss.evidence.dangling_markup.img_src_swallows_following_page_markup`
- **Assigning to element.innerHTML does not run an injected <script> element on any modern browser, so a DOM XSS payload aimed at that sink must instead use an element whose event fires on parse failure, such as an <img> with an invalid src and an onerror handler.**
  - kills it if: The claim is wrong if the target browser is one that still executes script elements inserted via innerHTML, since that pre-existing behaviour was never removed from the HTML fragment parsing algorithm in every engine. It is also wrong if the sink is document.write or document.writeln rather than innerHTML, because those go through the full parser and do run a script element. It is additionally wrong for a sink that later re-reads the .innerHTML property and passes it to document.write or eval, where the script element executes after the second step. And it is wrong where Trusted Types enforcement is on and the assignment throws before any parsing happens.
  - `xss.evidence.dom_sink.innerhtml_ignores_script_element_needs_event_handler`
- **A postMessage listener that never reads event.origin accepts a message from any site, and because any window in the iframe hierarchy can reach the handler top-down, the receiver must check the origin against an allow-list before acting on event.data.**
  - kills it if: The claim is wrong if the receiver does validate e.origin against an allow-list before touching e.data, since then a forged-origin message is rejected and nothing executes - the listener existing is not the finding. It is also wrong if the sink inside the handler is not reachable with attacker-chosen data, for example the handler reads only a fixed key and never assigns a value into innerHTML, eval, or a script src. And it is wrong if the handler validates both origin and the syntax of the received message and re-validates before use, because MDN notes that an unvalidated message body from an otherwise trusted sender can itself be the XSS hole.
  - `xss.evidence.postmessage.origin_check_must_be_allowlist_on_receiver`
- **A client-side prototype pollution source plus a config object that falls back to a default option becomes script execution when the library writes that inherited option into a script element's src and appends it to the document.**
  - kills it if: The claim is wrong if the config object defines its own transport_url property, because an object's own property takes precedence over anything inherited from the prototype and the gadget cannot fire. It is also wrong if the object is created with a null prototype or if Object.prototype is frozen or sealed, since then nothing is inherited and nothing to pollute. It is wrong if the sink is not reached - for example the library only builds a URL string for display and never assigns it to a fetching property. And it is wrong if a CSP restricts script-src to the origin's own domain, in which case the appended script is blocked and the chain stops at the network request rather than executing.
  - `xss.evidence.prototype_pollution.transport_url_gadget_reaches_script_src`
- **With require-trusted-types-for enforced, a DOM sink that receives a plain string does not silently sanitise it - the browser attempts to obtain a TrustedScript from a default policy and, if none is defined or none returns one, the operation throws an exception instead of executing.**
  - kills it if: The claim is wrong if a default policy is defined and its transformation function returns the input unchanged, for example a policy built with DOMPurify replaced by an identity function - the sink then receives a TrustedScript and the exception never fires. It is also wrong for an indirect sink that bypasses the check, such as assigning to innerText on a script element or building a script element from a text node, where in some engine versions the check is not applied at the point of assignment. It is wrong where require-trusted-types-for is not actually in the delivered policy header, including the case where the header is present but a report-only variant is used. And it is wrong on browsers that do not implement Trusted Types at all, where the payload runs unchanged.
  - `xss.evidence.trusted_types.sink_throws_when_no_default_policy_returns_trustedscript`

## Applies to every XSS sub-type

_False-positive rules, validation bars and escalation steps that are not specific to this delivery type. Canonical copies live in `domains/web/xss/knowledge/CLASS.md` and `domains/web/xss/skills/SKILL.md`; they are listed here so this file can be used on its own._

- **A CSP only blocks inline or foreign script execution; nonces, hashes and strict-dynamic decide whether an injected payload can still run.**
  - kills it if: The policy is nonce- or hash-based with an unguessable per-load nonce and no unsafe-inline, and the payload yields no element carrying a matching nonce or hash.
  - `xss.bypass.csp_nonce_hash_or_strict_dynamic_gap`
- **HTML-encoding characters the filter blocks defeats it inside an event-handler attribute, because the browser HTML-decodes attribute values before JavaScript runs.**
  - kills it if: This is wrong if the browser decodes the attribute only once and the application re-encodes after decoding, or if the sink is textContent or a DOM property that receives the still-encoded value without HTML decoding.
  - `xss.bypass.filter.html_entity_decoding_of_attribute_values`
- **A filter blocking parentheses is bypassed by invoking the function without them, for example with a throw statement and a global exception handler.**
  - kills it if: This is wrong if the filter also blocks the throw keyword, the semicolon, or the equals sign, or if the application CSP forbids inline handlers so no assignment is ever reached.
  - `xss.bypass.filter.parentheses_free_invocation`
- **A nonce-based CSP only blocks injected inline script, so DOM sinks and dangling markup remain exploitable under the same policy.**
  - kills it if: This is wrong if the policy is nonce- or hash-based with an unguessable per-load nonce and the payload yields no element carrying a matching nonce or hash AND no other reachable sink exists.
  - `xss.bypass.trusted_types.dom_sink_requires_policy`
- **HttpOnly and SameSite cookie attributes block cookie exfiltration and cross-site request delivery but do not stop same-origin injected script from acting through the victim's session, so a hardened cookie posture is not an XSS mitigation.**
  - kills it if: If the same-origin request is sent without the session cookie while an identical hand-crafted request from the same origin does carry it, the cookie is being withheld for a reason other than SameSite and the claim does not describe this target.
  - `xss.chain_link.cookie_posture.httponly_and_samesite_do_not_block_same_origin_script`
- **An anti-CSRF token provides no protection against XSS, because script executing in the victim's origin can read the token out of the page or the response and replay the state-changing request with it.**
  - kills it if: If the state-changing request is refused with a token-validation error even when the script supplies the token read from the same page, the defence is holding and this chain link does not apply to that endpoint.
  - `xss.chain_link.csrf_token_read_defeats_csrf_defence`
- **Changing the account email address from injected script and then triggering the normal password-reset flow yields full account takeover without ever stealing a session cookie.**
  - kills it if: If the email-change endpoint re-authenticates the user or re-sends the current password before it will change the address, or if the reset mail still goes only to the original address, the takeover step fails and this chain link does not apply.
  - `xss.chain_link.email_change_then_password_reset_takes_over_account`
- **Client-side prototype pollution chains into DOM XSS when a polluted prototype property is later consumed as an unsafe sink value.**
  - kills it if: The merge routine rejects or ignores __proto__ and constructor keys, or no sink reads any property an attacker can pollute on Object.prototype.
  - `xss.chain_link.prototype_pollution_to_dom_xss`
- **Once injected script executes in the victim's origin it inherits every action the victim's authenticated session can perform, so the impact ceiling is the victim's own account authority rather than a popup.**
  - kills it if: If the same-origin request made from the injected script is rejected as unauthenticated, or returns the same body as an anonymous session, then the script is not running with the victim's session authority and the claim's ceiling does not apply to that finding.
  - `xss.chain_link.same_origin_authority.victim_session_actions`
- **A stored payload submitted through a low-privilege account that later renders inside an administrator's session escalates a self-XSS into administrator compromise, and proving it requires two distinct identities.**
  - kills it if: If the payload fires only in the submitting account's own session and never renders in a second, higher-privileged user's view, then it is self-XSS and the escalation step is unproven.
  - `xss.chain_link.stored_payload_reaching_an_administrator_view`
- **When a site reflects attacker input into its own Content-Security-Policy - typically the trailing report-uri directive - a semicolon lets the attacker append directives, and the script-src-elem directive lets an appended script-src overwrite the existing nonce or hash based script-src entirely.**
  - kills it if: The claim is wrong if the site does not reflect any input into the policy, since there is then nothing to inject and the nonce stands. It is also wrong if the reflected value is filtered so a semicolon or a comma cannot appear, because then no new directive can be opened. It is wrong for browsers that do not implement script-src-elem, where an appended script-src would simply be dropped as a duplicate and the original policy would still apply. And it is wrong for servers that deliver the policy as a meta tag rather than a header in a context where the attacker controls only part of the value, since the injected text is then inert element content rather than a directive.
  - `xss.evidence.csp.script_src_elem_overwrite_defeats_nonce_policy`
- **Reject a DOM or reflected XSS candidate when the live page ships a CSP whose script-src carries a nonce or hash source without unsafe-inline and without strict-dynamic, because your injected inline script and inline event handlers cannot execute.**
  - kills it if: The rule is wrong when the policy contains 'unsafe-inline' (or 'unsafe-eval' for eval-style payloads), or when strict-dynamic is present and the injection point runs on a page that already loaded a nonced/hash-trusted script - in both cases a nonce-less injected script is executed anyway and the finding is a full XSS. It is also wrong if the CSP is only a report-only header (Content-Security-Policy-Report-Only), which logs violations without blocking anything.
  - `xss.fp_rule.csp.live_nonce_or_hash_policy_blocks_payload`
- **Reject a DOM clobbering or prototype-pollution XSS candidate when the clobbered or polluted property is only read as a string into textContent, an attribute or a URL fetch, and never reaches an HTML parser or script-execution context.**
  - kills it if: The rule is wrong if the clobbered or polluted property is later assigned into an HTML-executing sink - a clobbered script src/iframe src whose value navigates to attacker markup, or a polluted property consumed by a template that renders it as HTML - because that is script execution with an injection-only primitive, and it is a real XSS. OWASP's own note that CSP mitigates clobbering of script sources but not already-present code that can be abused for execution is the same distinction seen from the mitigation side.
  - `xss.fp_rule.dom_clobbering.property_read_into_safe_sink`
- **Reject a reflected XSS candidate when the reflected value appears in the response only as HTML entities or percent/unicode escapes that the browser decodes back to inert text in that context, because encoding is what makes the reflection non-exploitable.**
  - kills it if: The rule is wrong if the encoding is applied for the wrong context - for example only HTML-entity-encoded output dropped inside a JavaScript string, a URL, a CSS value or an unquoted attribute, where &quot; and &#39; do not neutralise a quote delimiter and a ';alert(1)// payload still breaks the string. It is also wrong if the entity is decoded and re-serialised anywhere before rendering (a client-side read of .innerHTML followed by a re-write, or a client-side template that re-interprets the text as HTML), because then the inert text becomes live markup.
  - `xss.fp_rule.html_encoding.entity_encoded_reflection_cannot_break_context`
- **Reject a JSON API endpoint reported as XSS when the response Content-Type is application/json and no client-side code path inserts the reflected value into an HTML document.**
  - kills it if: The rule is wrong if the same reflected value reaches an HTML-executing context through any code path: the API is called by a front end that assigns the response into innerHTML or a framework's raw-HTML binding, the endpoint is reachable at the same path with a text/html or JSONP callback content type, or the server renders the stored value into an HTML page for other users. Then the JSON body is only the delivery mechanism, and the finding is a genuine XSS located at the sink.
  - `xss.fp_rule.json_api.content_type_json_is_not_html_execution`
- **Injection that survives a server-side markup-to-HTML renderer (Markdown, Textile, wiki syntax) but never reaches a script-execution context in the delivered page is a content-injection issue, not XSS, and must not be reported as XSS without a browser-confirmed execution trace.**
  - kills it if: The rule collapses when the rendered markup is later consumed by a sink: a client-side viewer that fetches the same field and assigns it to innerHTML, a print/export pipeline that re-injects it, an email client that renders it, or a second page that echoes the raw stored value. It is also wrong if the renderer emits script-capable constructs by design - raw HTML passthrough, a custom block that permits <iframe>, inline event handlers, or javascript: links - in which case the renderer's own output is the sink and the injection is XSS. And a payload confirmed executing in a real browser, with a second observable such as a network beacon, is XSS by definition regardless of which stage introduced it.
  - `xss.fp_rule.markup_renderer_output_is_not_execution_until_a_second_stage_sink`
- **Reject a prototype-pollution finding reported as XSS unless the polluted property value is read back and written into an HTML-executing sink, because polluting Object.prototype alone executes no script in any page.**
  - kills it if: The rule is wrong if the polluted property is consumed by a templating engine or a client-side render that inserts it as markup - a server-side template interpolating the inherited property, or front-end code writing it to innerHTML or a raw-HTML framework binding - because then the pollution is the injection primitive and the result is stored XSS reachable by every user of the app. Equally, if the pollution reaches a code-execution gadget (a template engine option object, a child-process invocation), that is RCE, which is a stronger finding than the XSS report claimed.
  - `xss.fp_rule.prototype_pollution.property_write_is_not_html_injection`
- **A reflected XSS on an anonymous, read-only page is not automatically informational; it still executes script in every visitor's origin.**
  - kills it if: The page's origin exposes no authenticated state, no same-origin privileged endpoints and no tokens reachable from injected script, leaving only a bare popup.
  - `xss.fp_rule.readonly_brochureware_page_does_not_clear_xss`
- **User input echoed verbatim into a response served with Content-Type: application/json, text/plain, or application/octet-stream is not reflected XSS unless the browser can be made to parse that response as HTML: XSS requires the payload to reach an HTML or script execution context, not merely to be reflected.**
  - kills it if: It IS XSS if the same parameter also lands in an HTML response, if the Content-Type is absent or set to a sniffable value so a browser renders it as HTML, or if the API output is later written into the DOM through an unsafe sink (innerHTML, document.write, eval). Test the sink path, not the echo.
  - `xss.fp_rule.reflected_input_in_non_html_response_is_not_xss`
- **A filter that only deletes the literal string "script" from user input is not a control at all: the surrounding angle brackets survive, so the injected tag remains well-formed and still executes.**
  - kills it if: The rule is false if the filter is a real parser-based sanitiser rather than a substring delete - a tokenising HTML sanitiser that rebuilds the document from a permitted list of elements and attributes neutralises the split-tag payload because the brackets are consumed as part of a rejected tag, not left orphaned. It is also false if a downstream layer re-encodes or re-parses, or if the filter strips all angle brackets rather than a keyword. And the rule is only about the filter: if the value is separately output-escaped at render time, the split payload is inert regardless of what the filter did.
  - `xss.fp_rule.restricted_list_filter_that_deletes_a_keyword_leaves_a_live_payload`
- **Reject a sanitizer-bypass XSS claim when the rendered page shows the payload as inert text with the dangerous markup stripped, because a payload that does not become live DOM in the browser is not a bypass.**
  - kills it if: The rule is wrong if a real element with a live event handler or a navigable javascript:/data: URL is present in the rendered DOM and your callback endpoint receives the request - that is a genuine sanitizer bypass and a real XSS, even if the sanitizer appeared to strip <script>. The rule also does not apply where the string is sanitized and then mutated or re-serialised before insertion, since the protection can be voided downstream; check the sink, not the sanitizer call.
  - `xss.fp_rule.sanitizer.output_observed_inert_in_page`
- **Reject an XSS candidate as unproven when the payload can only be made to render by pasting attacker-supplied JavaScript into the submitter's own address bar or console, because that is self-XSS and not a cross-user finding.**
  - kills it if: The candidate stops being self-XSS the moment a working delivery exists: a crafted URL (or a CSRF-style auto-submitting form) that fires the payload automatically in any other user's browser, on a page an authenticated victim visits. Then it is ordinary reflected XSS and this rejection rule is wrong. Equally, if the 'pasting' step is not required because the value is stored and later rendered to other users, the finding is stored XSS, not self-XSS.
  - `xss.fp_rule.self_xss.payload_renders_only_in_submitter_browser`
- **Reject a DOM-based XSS candidate when the traced attacker-controlled source only ever reaches textContent, innerText, or setAttribute with a hardcoded non-event attribute, because those sinks treat the value as text and never parse it as markup.**
  - kills it if: The candidate is a real DOM XSS if the identical tainted value, in the identical code path, is also passed to an execution-capable sink - innerHTML/outerHTML/insertAdjacentHTML/document.write/eval/string setTimeout - anywhere the same value can reach on another page load, in a fallback branch, or for a different input shape. This rule is also wrong if setAttribute's attribute NAME is derived from the same tainted input (setAttribute(t, v) where t is user-influenced), because OWASP limits setAttribute's safety to hardcoded, innocuous attribute names; an injected name such as onmouseover re-creates an injection sink.
  - `xss.fp_rule.sink_reachability.source_never_reaches_execution_sink`
- **Reject a stored XSS candidate when the submitted payload never appears in any response served to another user or role, because a store-only write with no second-user render is not cross-site script execution.**
  - kills it if: The rule is wrong if any second surface renders the stored value - an admin moderation queue, a different user's listing or profile page, a notification email, an export/CSV/PDF generator, a webhook payload or a third-party integration that re-renders the string as HTML. Any one of those makes it genuine stored XSS, because the hunter now has two distinct steps: store, then a second user's response executes it.
  - `xss.fp_rule.stored_xss.entry_point_never_reaches_second_user_view`
- **A value that reaches a page only through a client-side template's escaped interpolation or attribute binding is not XSS, because the framework assigns it through textContent/setAttribute rather than by string-concatenating it into markup.**
  - kills it if: The rule is wrong the moment the value is also passed to a raw-HTML sink on the same render path (v-html, innerHTML, a markdown-to-HTML renderer, a server-side {{ triple-brace or |safe filter) - the framework's escaping applies only to the escaped bindings, and one raw sink is enough. It is also wrong if the value is echoed into a context the template engine does not own at all, such as a JSON blob later read by another script and written to a sink, or a value concatenated into an inline <script> block. Finally it is wrong if the app is not the framework it appears to be on some route - a JSON API or a server-rendered fragment served outside the template engine lands the string in raw HTML.
  - `xss.fp_rule.template_interpolation_is_escaped_by_the_framework_not_by_the_response`
- **Serving the vulnerable page over HTTPS changes nothing about the attack, because same-origin script execution is scoped by origin, and https is part of the origin definition rather than a barrier to it.**
  - kills it if: If the payload only executes on a plaintext HTTP origin and the browser blocks it or the application serves different content over HTTPS, then the scheme does affect the finding and this claim does not hold for it.
  - `xss.impact.transport_security.tls_does_not_mitigate_same_origin_execution`
- **A JSON response served as text/html and interpolated into a page becomes an HTML injection point even though the body is JSON.**
  - kills it if: The endpoint returns application/json and no code path inserts the response body into an HTML document, so injected markup is never parsed as markup.
  - `xss.technique.json_response.embedded_into_html_document`
- **An escape routine that is correct for one context does not protect another, so a finding is wrong until the encoding is shown to match the exact context the value lands in.**
  - kills it if: This is wrong if the value is context-correctly encoded by a vetted encoder for its exact destination, or if it is inserted as a property value on a sink that encodes automatically.
  - `xss.validation.encoding_must_match_landing_context`
- **A payload that fires an alert only in the hunter's own browser demonstrates script execution but not a reportable vulnerability, because impact requires the payload to reach another user's session or a reachable victim path.**
  - kills it if: If the payload demonstrably renders and executes in a second, independently authenticated session or in a view reached by another user, then the marker is not self-only and the finding does clear the bar.
  - `xss.validation.self_fired_marker_is_not_a_reportable_finding`
