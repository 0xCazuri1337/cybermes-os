## New items admitted (2, both promoted, both citing 2 independent publishers)

### 1. `linux_privesc.technique.file_capability_xattr_raises_permitted_set`
A non-empty `security.capability` extended attribute on an executable places
that capability set into the thread's permitted set at execve.

- **Publishers:** `cwe.mitre.org` + `man7.org` (the canonical Linux man-pages
  publisher — the authoritative source for execve/capability semantics).
- **Disproof recorded:** the claim is wrong on a kernel built without
  file-capability support, where the capability bits are notionally all present
  and the bounding set does not restrict them.
- **Hunting value:** a file-capability binary in a world-writable directory or a
  user-writable upload path is a root path with no exploit primitive required.

### 2. `linux_privesc.technique.writable_core_pattern_pipe_executes_handler_as_root`
When `/proc/sys/kernel/core_pattern` begins with a pipe character, the kernel
treats the remainder of the line as a command to execute — which runs as root
on crash.

- **Publishers:** `cwe.mitre.org` + `man7.org`.
- **Disproof recorded:** the claim fails when `core_pattern` is root-owned mode
  `0644` inside a read-only or correctly restricted `/proc`, i.e. when the
  prerequisite write is not available.

**Shared precondition, and the reason both are in the same family:** both reduce
to *a root-owned, mode-0644 `/proc/sys` entry that an unprivileged user must be
able to write*. That is the actual hunt target — the two techniques are
downstream of one primitive, and a tester who cannot write `core_pattern` cannot
use either. `HUNT.md` renders both to the same procedure shape for that reason.
