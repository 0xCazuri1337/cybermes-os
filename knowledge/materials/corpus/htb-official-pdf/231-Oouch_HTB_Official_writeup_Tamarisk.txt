Synopsis

Oouch is a hard difficulty Linux machine featuring web applications that use the OAuth
authorization framework. Absence of a CSRF Token is leveraged to link an administrative account
to our account, providing access to sensitive information. This information is used to register a
new client application and steal the authorization code. This code is used to gain an access token,
which provides unrestricted access to user resources. A misconfigured DBus server is then
exploited through uWSGI in order to execute code in the context of root.

The file doesn't contain much information, but it provides us with the two terms Consumer and
Authorization Server . A quick Google reveals that these terms are associated with OAuth
terminology.

OAuth is an authorization protocol that allows third party applications to access user accounts
from external HTTP services. It works by sharing user authorization tokens, which are used to act
on behalf of the user who authorizes the application. This removes the requirement for providing
explicit credentials and relying solely on the information provided by the authorization server.
For example, the application above permits us to login using explicitly provided credentials (email
and password), or by delegated authentication to Google, Microsoft or Apple.

There are four roles defined by OAuth:

      Resource owner: This is the end-user who owns the user account on the authorization
      server.
      Client: This is the third party application (Atlassian) that requests the resource owner grant
      access to the account. This is also referred to as the "Consumer".
      Resource server: This is the server that hosts the resources needed by the client
      application.
      Authorization server: This server grants access tokens to the client server after a
      successful authorization request (Google, Microsoft).

Usually, the resource and authorization server are present on the same server. However, they
can be hosted separately as well.

The OAuth 2.0 RFC highlights the flow of the protocol.
The flow starts with the resource owner (user) granting the authorization request from the client.
The client then relays this to the authorization server in order to obtain an access token for the
resource. This token is passed to the resource server, which returns any requested resources,
such as user information.
The project.txt file informs us that the consumer (client) application is hosted on a Flask
server, while the authorization server is Django.

Generating an Access Token

Now that we have a valid authorization code, we can use it to generate an access token. This is
done by the authorization server internally. However we already know about the /oauth/token
endpoint.
The Django OAuth documentation shows how a token can be requested using cURL.

   curl -X POST -d "grant_type=<grant_type>&client_id=
   <your_client_id>&client_secret=<your_client_secret>&code=<code>"
   http://localhost:8000/o/token/

The client_id , client_secret and grant_type are already know to us via the application
registration, while the code parameter is the token we received.

Privilege Escalation

The note talks about an IPS (Intrusion Prevention System) implemented using DBus and iptables.

DBus on the other hand, is a message bus system used for inter-application communication.

uWSGI

Unlike HTTP, uWSGI uses a binary protocol for communication. This means we can't
communicate with it using plain HTTP requests. We can use the uwsgi-tools project as a reference
to create a script which can communicate with the socket.
Firstly, we'll need the packet structure present in uwsgi-structs.py file. This structure represents
the packet header recognized by the uWSGI protocol as shown here. Next, we'll need
pack_uwsgi_vars() from utils.py file. This method does nothing but put together the packet as
a byte array.

This method puts together the data in its required format. The project doesn't support
communication over a Unix socket, which means that we'll have to implement this manually.
