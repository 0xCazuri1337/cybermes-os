# interpret — result → meaning → next action

Most open-redirect hunts end in one of the ambiguous rows below, not in a clean
proof. Each row names the next action, because "inconclusive" is where the hunt
dies if it is treated as a no.

---

## Clean results

| Result | Meaning | Next action |
|---|---|---|
| 3xx whose `Location` resolves to a host I control, redirect not followed, captured in a raw exchange | Proved. This is the validation bar: reaching a controlled host through the parameter with the `Location` header captured, not the presence of a 302 alone [open_redirect.validation.destination_allowlist_must_be_probed]. | Move to severity triage (post-auth hop? feeds OAuth?) [open_redirect.evidence.the_meaningful_observation_is_the_unvalidated_destination_after_login_not_before_it]. |
| `Location` string contains my host but the **parsed** authority is different (userinfo, backslash, confusable) | The app validated a raw string, not an authority. Mechanism = bypass, not missing validation. [open_redirect.bypass.a_hostname_allowlist_checked_without_url_parsing_is_defeated_by_a_confusable_host] | Report as a **blocklist/naive-string-check bypass** with the parser evidence attached. Do not write "no validation". |
| Protocol-relative `//host` survives a scheme-based check | Host termination broke without a scheme ever being present — a distinct failure from scheme parsing. [open_redirect.fp_rule.redirect_to_relative_path_on_same_origin_is_not_open] | Report the specific family so the fix closes relative/scheme-relative input, which is the named closing condition [open_redirect.bypass.a_hostname_allowlist_checked_without_url_parsing_is_defeated_by_a_confusable_host]. |
| Every observed `Location` resolves to the request origin | Not an open redirect. No phishing pivot, no leakage to a foreign authority. [open_redirect.fp_rule.redirect_to_relative_path_on_same_origin_is_not_open] | Reject; record which variants were tried. |
| Server-side resolution says same-origin, a real browser says otherwise | The value is being resolved by a client, not the server — the server-side check passes while the user agent still leaves the origin. [open_redirect.fp_rule.a_same_site_relative_path_redirect_is_not_an_open_redirect] | **Do not reject.** Re-test in a real browser; the same-site rule is scoped to server-side resolution [open_redirect.fp_rule.a_same_site_relative_path_redirect_is_not_an_open_redirect]. |

## Ambiguous results — the ones that decide hunts

| Result | Meaning | Next action |
|---|---|---|
| **The browser refuses to follow** and shows a safe-browsing / phishing interstitial instead of landing on my page | The server-side trust decision still failed — the 302 *was* emitted with my host in `Location`. The refusal is a **client-side mitigation**, not a server-side control. Reading it as "safe, not a finding" is the classic mis-parse. | Record the raw 3xx as the proof [open_redirect.validation.proof_is_the_location_header_of_an_actual_302_not_the_presence_of_a_url_parameter], note the interstitial as defence-in-depth that varies by user agent, and **re-validate with redirects not auto-followed** so the headers are observable [open_redirect.validation.proof_is_the_location_header_of_an_actual_302_not_the_presence_of_a_url_parameter]. Do not let a user-agent warning downgrade the finding: the same-url-is-safe rule is about whether the browser *can* be moved off the origin [open_redirect.fp_rule.redirect_to_relative_path_on_same_origin_is_not_open]. |
| **The endpoint sits behind authentication** — the redirect only fires for a logged-in session, so an anonymous probe gets a login page and a 200 | Absence of a 302 is not absence of the bug. The unobserved hop is precisely the consequential one: the post-authentication redirect lands the user on the attacker's page already carrying a fresh session [open_redirect.evidence.the_meaningful_observation_is_the_unvalidated_destination_after_login_not_before_it]. | Test with an authenticated session **and** the redirect-following disabled. The login-bounce parameter is the documented fuzz target for exactly this shape — the redirect parameter carried in a login URL is the post-login destination the user influences [open_redirect.technique.hth_if_the_site_prompts_for_a_login]. Its disproof is a parameter that refuses external hosts or always resolves to a fixed internal path [open_redirect.technique.hth_if_the_site_prompts_for_a_login] — so "it bounced me to login" is not itself a result, it is the setup. |
| **A 302 whose `Location` points at the same URL** (self-redirect / refresh loop) | A loop, not a redirect. The authority equals the request host, so nothing leaves the origin — exactly the same-origin case: a 302 whose `Location` is a same-origin path or an absolute URL whose authority equals the request `Host` cannot move the browser off the origin [open_redirect.fp_rule.redirect_to_relative_path_on_same_origin_is_not_open]. | Reject as an open redirect. Chasing the loop is wasted time. **But** verify it is a *fixed* self-redirect and not an echo of an attacker value into the same URL, which the corpus's false-positive log explicitly rejects: a same-host 302 with the parameter echoed is not a finding because no request ever left the origin. |
| **Meta-refresh / client-side navigation instead of a 3xx** | Different mechanism, same impact. The 3xx class is defined as further action needing to be taken by the user agent, carried in `Location` [open_redirect.evidence.automatic_redirection_needs_to_done_with_car] [open_redirect.evidence.if_a_location_header_field_section_7_1_2_is] — a `<meta http-equiv=refresh>` produces the same origin change with no 3xx at all. | Same proof requirement, different artefact: the `Location`-header proof bar does not literally cover it, so capture the rendered page's navigational directive as the request/response pair, and be explicit in the report that the proof is not a 302. **Scope note (inference, not a corpus item):** the corpus's proof item is stated for a 3xx `Location` [open_redirect.validation.proof_is_the_location_header_of_an_actual_302_not_the_presence_of_a_url_parameter], so a meta-refresh finding must argue its impact from the same invariant — destination origin chosen by the request rather than the application [open_redirect.signal.user_input_reaches_redirect_destination] — not from the 3xx wording. |
| **OAuth endpoint answers `redirect_uri_mismatch`** | The authorisation server refused the unregistered destination; its defence worked. Must not be reported as an open redirect on the client. [open_redirect.fp_rule.an_oauth_redirect_uri_mismatch_error_is_a_rejected_request_not_an_open_redirect] | Reject **for that variant only**. The rule is wrong when the client holds a pre-registered wildcard or prefix pattern the server honours, or when a weaker registered form still accepts the malicious origin [open_redirect.fp_rule.an_oauth_redirect_uri_mismatch_error_is_a_rejected_request_not_an_open_redirect] — so try variant families before closing. |
| **Redirect to an external origin with a client id the tenant never registered** | This is the disproof condition for the sibling FP: an arbitrary external destination reachable that way shows the redirection value is attacker-supplied in the request rather than tenant-configured. [open_redirect.fp_rule.registered_oauth_redirect_uri_is_not_a_webapp_open_redirect] | Escalate — it is now a finding, not a false positive. |

## Negative and null results — where hunts actually die

| Result | Meaning | Next action |
|---|---|---|
| Controlled host never appears in any `Location` across absolute, relative and near-miss variants | The redirect is not user-controllable. Validation fails. [open_redirect.validation.destination_allowlist_must_be_probed] | Stop. Do not report on parameter presence alone [open_redirect.validation.proof_is_the_location_header_of_an_actual_302_not_the_presence_of_a_url_parameter]. |
| A `next`/`returnUrl` parameter exists but the destination is always a fixed internal route | The signal's own exclusion applies: if no supplied parameter alters the `Location` host, there is no open redirect to pursue. [open_redirect.signal.user_input_reaches_redirect_destination] | Stop; move to the next endpoint. |
| Response identical in every case; nothing reflected | The test does not apply — no surrounding behaviour observable. [open_redirect.test.an_open_redirect_is_proved_by_a_3xx_response_who] | Stop; this is an unobservable boundary, not a negative finding. |
| I only have a screenshot of the final page | Insufficient evidence — the `Location` must be captured from a raw exchange or a network log. [open_redirect.validation.proof_is_the_location_header_of_an_actual_302_not_the_presence_of_a_url_parameter] | Re-capture. |
| I validated with HEAD and got no body | HEAD terminates at the end of the header section; there was nothing to read. [open_redirect.evidence.a_payload_within_a_get_request_message_has_n] [open_redirect.evidence.the_server_should_send_the_same_header_field] | Re-run with GET. |
| I only saw a 200 with the parameter on it | Proves nothing. [open_redirect.validation.proof_is_the_location_header_of_an_actual_302_not_the_presence_of_a_url_parameter] | Go back to Step 0/1 of `test`. |
