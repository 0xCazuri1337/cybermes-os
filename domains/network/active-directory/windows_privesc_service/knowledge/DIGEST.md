# Windows Privilege Escalation via Service and Named-Pipe Abuse

> surface: `ad` · CWE: CWE-269 · OWASP: A04:2021
> maturity: **mature** — 12 items, 10 supported, 2 FP rules, 1 chains

A privileged service is induced to load or impersonate an attacker-chosen identity, so the escalation runs with SYSTEM through a legitimate service entry point.

## Technique

- **An endpoint agent's SYSTEM service that accepts the update server address over an unauthenticated localhost IPC channel and installs whatever MSI that server returns lets a local user redirect the service's update source, so the SYSTEM service's own installer runs attacker code as NT AUTHORITY\SYSTEM.**  
  `high_confidence` · score 0.869 · disproved by: Refuted when the agent pins its update endpoint to a fixed allow-list that refuses the rogue host, when it validates the returned package against a vendor certificate chain rather than any publicly-signed certificate, or when the IPC command needs an administrator-authenticated token: without both the redirect and the attacker-signed MSI install succeeding, the service never runs attacker code.
  sources: <https://services.nvd.nist.gov/rest/json/cves/2.0?cveId=CVE-2025-0309> · <https://raw.githubusercontent.com/HackTricks-wiki/hacktricks/master/src/windows-hardening/windows-local-privilege-escalation/abusing-auto-updaters-and-ipc.md>
- **A service registry key where a non-administrator holds only KEY_CREATE_SUB_KEY cannot have its existing values edited, but creating the legacy Performance subkey with Library, Open, Collect and Close names makes the next privileged performance counter consumer load an attacker-chosen DLL inside its own process, so subkey-only write access becomes privilege escalation as NT AUTHORITY\SYSTEM.**  
  `high_confidence` · score 0.855 · disproved by: Refuted when the service key grants the caller no subkey-create right, when a `Disable Performance Counters` value already exists on that key, or when the only consumer reachable is a process the attacker already controls (perfmon run as the attacker) - the DLL has to load inside a process that is already SYSTEM for the escalation to hold.
  sources: <https://learn.microsoft.com/en-us/windows/win32/perfctrs/about-performance-counters> · <https://learn.microsoft.com/en-us/windows/win32/perfctrs/creating-the-applications-performance-key> · <https://raw.githubusercontent.com/HackTricks-wiki/hacktricks/master/src/windows-hardening/windows-local-privilege-escalation/appenddata-addsubdirectory-permission-over-service-registry.md>
- **Service trigger conditions such as a named-pipe connection attempt let an attacker force a privileged service to start, so trigger conditions are themselves a service-start primitive.**  
  `high_confidence` · score 0.83 · disproved by: The target service has no trigger registered, or the condition cannot be satisfied from the attacker's context.
  sources: <https://cwe.mitre.org/data/definitions/269.html> · <https://learn.microsoft.com/en-us/windows/win32/services/service-security-and-access-rights> · <https://raw.githubusercontent.com/HackTricks-wiki/hacktricks/master/src/windows-hardening/windows-local-privilege-escalation/service-triggers.md>
- **The complete named-pipe client impersonation chain requires both SeImpersonatePrivilege and a privileged client such as a SYSTEM service that will connect to an attacker-created pipe, after which the resulting token is duplicated into a primary token for the spawned process.**  
  `high_confidence` · score 0.83 · disproved by: SeImpersonatePrivilege is absent, or no privileged client can be coerced to connect to a rogue pipe instance.
  sources: <https://cwe.mitre.org/data/definitions/269.html> · <https://learn.microsoft.com/en-us/windows/win32/services/service-security-and-access-rights> · <https://raw.githubusercontent.com/HackTricks-wiki/hacktricks/master/src/windows-hardening/windows-local-privilege-escalation/named-pipe-client-impersonation.md>
- **Any named-pipe server that a privileged client connects to can be turned into that client's privileges by calling ImpersonateNamedPipeClient, making pipe ACLs and client reachability the deciding factors.**  
  `high_confidence` · score 0.83 · disproved by: The pipe server never impersonates its client, or no privileged client can reach the pipe.
  sources: <https://cwe.mitre.org/data/definitions/269.html> · <https://learn.microsoft.com/en-us/windows/win32/services/service-security-and-access-rights> · <https://raw.githubusercontent.com/HackTricks-wiki/hacktricks/master/src/windows-hardening/windows-local-privilege-escalation/named-pipe-client-impersonation.md>
- **Because FILE_CREATE_PIPE_INSTANCE shares its access bit with FILE_APPEND_DATA, a low-privilege user can squat a second server instance under a privileged pipe's name and, since instances are matched FIFO, receive real clients and relay or desynchronize their privileged IPC.**  
  `high_confidence` · score 0.83 · disproved by: The privileged pipe is created without FILE_APPEND_DATA, or instance matching does not place the attacker's instance ahead of legitimate ones.
  sources: <https://cwe.mitre.org/data/definitions/269.html> · <https://learn.microsoft.com/en-us/windows/win32/services/service-security-and-access-rights> · <https://raw.githubusercontent.com/HackTricks-wiki/hacktricks/master/src/windows-hardening/windows-local-privilege-escalation/named-pipe-client-impersonation.md>
- **Starting dormant built-in services such as RemoteRegistry, WebClient/WebDAV or EFS creates new RPC and named-pipe listeners, so a mere service-start primitive chains into further attack surface.**  
  `high_confidence` · score 0.83 · disproved by: The services cannot be started by a non-privileged caller, or starting them exposes no new listeners.
  sources: <https://cwe.mitre.org/data/definitions/269.html> · <https://learn.microsoft.com/en-us/windows/win32/services/service-security-and-access-rights> · <https://raw.githubusercontent.com/HackTricks-wiki/hacktricks/master/src/windows-hardening/windows-local-privilege-escalation/service-triggers.md>
- **A service object whose DACL grants a non-administrator SERVICE_CHANGE_CONFIG lets that user call ChangeServiceConfig and rewrite the service binary path the Service Control Manager runs, so the next start of that service executes attacker-chosen code as the service account.**  
  `under_review` · score 0.8115 · disproved by: Refuted when `sc sdshow <service>` shows no non-administrator ACE carrying SERVICE_CHANGE_CONFIG or WRITE_DAC, or when the SCM refuses or resets the rewritten binpath: the reconfigured command must actually be the one launched under the service account, and a service that is disabled and cannot be started demonstrates no execution.
  sources: <https://learn.microsoft.com/en-us/windows/win32/services/service-security-and-access-rights> · <https://raw.githubusercontent.com/HackTricks-wiki/hacktricks/master/src/windows-hardening/windows-local-privilege-escalation/README.md>

## Test

- **SERVICE_CHANGE_CONFIG is the service access right that permits rewriting the binary path the Service Control Manager runs; a service DACL finding needs a non-administrator principal holding that right, not merely start or stop permission.**  
  `under_review` · score 0.784 · disproved by: The finding fails when the non-administrator principal has only start or stop rights, when SERVICE_CHANGE_CONFIG is absent from the effective DACL, or when ChangeServiceConfig is denied despite the apparent permission.
  sources: <https://learn.microsoft.com/en-us/windows/win32/services/service-security-and-access-rights> · <https://raw.githubusercontent.com/HackTricks-wiki/hacktricks/master/src/windows-hardening/windows-local-privilege-escalation/README.md>

## Fp Rule

- **Reject a windows_privesc_service finding until it is distinguished from the adjacent behaviour this class also covers. "The complete named-pipe client impersonation chain requires both SeImpersonatePrivilege and a privileged client such as a SYSTEM service that will connect to an attacker-created pipe, after which the resulting token is duplicated into a..." and "The Terminal Services RPC named pipe \pipe\LSM_API_service is itself a privesc surface: it allows enumerating logged-on sessions and starting a process with a selected user's token." share a surface and a symptom, so a response that matches the first is not evidence for it while the second remains possible.**  
  `high_confidence` · score 0.869 · disproved by: This rule is wrong if a controlled test shows the two behaviours can never co-occur on the same surface, or if the corpus entry for "The Terminal Services RPC named pipe \pipe\LSM_API_service is itself a" is out of date. In that case this class needs its false-positive guidance rewritten rather than deleted.

## Variant

- **The Terminal Services RPC named pipe \pipe\LSM_API_service is itself a privesc surface: it allows enumerating logged-on sessions and starting a process with a selected user's token.**  
  `high_confidence` · score 0.83 · disproved by: The named pipe is absent or ACLs prevent a non-privileged caller from reaching the session enumeration and token APIs.
