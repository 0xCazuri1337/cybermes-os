# Path Traversal / File Inclusion

> surface: `web` · CWE: CWE-22 · OWASP: A01:2021
> maturity: **mature** — 62 items, 44 supported, 2 FP rules, 1 chains

A filename or path built from user input escapes its intended directory.

**Aliases:** path traversal, directory traversal, lfi, rfi, file inclusion

## Prerequisite

- **Traversal requires a request-controlled string concatenated into a filesystem path with no canonicalisation or prefix check; a vulnerable version alone is not enough.**  
  `high_confidence` · score 0.9015 · disproved by: If the response is identical for a traversal payload and for a nonexistent file, or the value is canonicalised and stripped of parent segments before the open, there is no traversal sink.
  sources: <https://bishopfox.com/blog/looting-unifi-controllers-detecting-and-weaponizing-cve-2026-22557> · <https://snyk.io/blog/exploring-3-types-of-directory-traversal-vulnerabilities-in-c-c/>
- **The chain is gated on three conditions that must hold together: the nested remote fetch needs allow_url_fopen=On, the LFI sink must be permitted to include from the writable temp directory, and a path-disclosure primitive must reveal the live temp file name.**  
  `high_confidence` · score 0.808 · disproved by: Refuted if the chain still reaches execution on a host with allow_url_fopen=Off, or on a host with no path-disclosure primitive, or where the sink refuses paths inside the temp directory.
  sources: <https://blog.qualys.com/vulnerabilities-threat-research/2021/10/27/apache-http-server-path-traversal-remote-code-execution-cve-2021-41773-cve-2021-42013> · <https://raw.githubusercontent.com/HackTricks-wiki/hacktricks/master/src/pentesting-web/file-inclusion/lfi2rce-via-compress.zlib-+-php_stream_prefer_studio-+-path-disclosure.md>
- **Whether remote inclusion is even possible on a PHP target is decided by ini switches with different defaults, so every candidate LFI sink must be classified by which of allow_url_include and allow_url_fopen is actually on before it is called exploitable.**  
  `high_confidence` · score 0.808 · disproved by: Refuted if a target whose ini shows allow_url_include=On rejects a remote URL supplied to the include parameter, or if a target with allow_url_include=Off happily includes one.
  sources: <https://docs.djangoproject.com/en/5.0/howto/static-files/> · <https://raw.githubusercontent.com/HackTricks-wiki/hacktricks/master/src/pentesting-web/file-inclusion/README.md>
- **Before any temp-path brute force through an LFI sink, the tester must confirm the traversal reaches /proc at all, by walking /proc/<pid>/cmdline through the inclusion until worker-process strings show up.**  
  `under_review` · score 0.798 · disproved by: Refuted if /proc/<pid>/cmdline reads come back empty or error out through an LFI sink that successfully returns other known local files, showing the file inclusion cannot enumerate process metadata.
  sources: <https://httpwg.org/specs/rfc9110.html> · <https://raw.githubusercontent.com/HackTricks-wiki/hacktricks/master/src/pentesting-web/file-inclusion/lfi2rce-via-nginx-temp-files.md>

## Signal

- **On Java targets a path traversal request aimed at a directory frequently comes back as a directory listing, so a suspected traversal must be confirmed by whether the LFI response enumerates entries rather than returns file content.**  
  `high_confidence` · score 0.863 · disproved by: Refuted if the listing appears for a path that contains no traversal payload at all, or if the response for a non-existent path is identical to the response for the traversal path.
  sources: <https://docs.djangoproject.com/en/5.0/howto/static-files/> · <https://raw.githubusercontent.com/HackTricks-wiki/hacktricks/master/src/pentesting-web/file-inclusion/README.md>
- **The LFI race is lost when the temp file has already been unlinked by the time the inclusion request runs, so the two observables that decide it are whether the path still resolves and whether the path disclosure actually reached the tester through output buffering.**  
  `high_confidence` · score 0.8355 · disproved by: Refuted if the file inclusion succeeds repeatedly while the temp directory is non-writable and open_basedir is active, or if the disclosure output is clearly buffered yet the path still arrives at the tester.
  sources: <https://blog.qualys.com/vulnerabilities-threat-research/2021/10/27/apache-http-server-path-traversal-remote-code-execution-cve-2021-41773-cve-2021-42013> · <https://raw.githubusercontent.com/HackTricks-wiki/hacktricks/master/src/pentesting-web/file-inclusion/lfi2rce-via-compress.zlib-+-php_stream_prefer_studio-+-path-disclosure.md>

## Validation

- **Behaviour on a static-file prefix says nothing about a parameterised download handler, and the reverse holds too - each endpoint needs its own probe because the two are served by different code entirely.**  
  `high_confidence` · score 0.918 · disproved by: The claim is false when both surfaces are served by the same confined component - a single static-file handler in front of every asset class, or a CDN or object-store gateway that applies one prefix rule to all buckets - in which case the static route's behaviour is genuinely informative about the download route. It also fails when the static surface is served by the web server itself from a document root, since the server's own path handling is a separate implementation and equally consistent across every alias it serves. And a specific finding on either endpoint still stands on its own evidence; this rule is only about the transfer of conclusions between endpoints.
  sources: <https://docs.djangoproject.com/en/5.0/howto/static-files/> · <https://werkzeug.palletsprojects.com/en/stable/utils/>
- **Confirm an arbitrary file read by fetching a file that exists only on disk, not a resource bundled in the application's classpath or JAR.**  
  `under_review` · score 0.874 · disproved by: If a file that exists only on disk returns 404 or an error while the bundled asset returns 200, the read comes from the classpath and the finding is not actionable on that host.
  sources: <https://bishopfox.com/blog/looting-unifi-controllers-detecting-and-weaponizing-cve-2026-22557> · <https://projectdiscovery.io/blog/how-to-research-web-vulnerabilities>

## Fp Rule

- **A traversal payload that returns the same content as the baseline request is not a traversal; the path was normalized or rejected before the file layer.**  
  `under_review` · score 0.954 · disproved by: If the identical response is because a CDN or reverse proxy caches by URL prefix and ignores your dot segments, then a cache-busting query parameter that still returns the outside-directory file means the traversal is real and the cache was the only thing hiding it.
  sources: <https://blog.qualys.com/vulnerabilities-threat-research/2021/10/27/apache-http-server-path-traversal-remote-code-execution-cve-2021-41773-cve-2021-42013> · <https://projectdiscovery.io/blog/nuclei-templates-april-2026>
- **A filename=../../../etc/passwd payload sent in a URL path segment or a multipart/form-data filename that the front-end web server removes before the application sees it is not path traversal, because the ../ sequence that would escape the base directory is neutralised upstream of the filesystem call and the read resolves inside the intended directory.**  
  `high_confidence` · score 0.924 · disproved by: The rule stops being true when a context exists in which the sequence is not stripped — a query-string or JSON body parameter, a header such as X-Forwarded-Prefix, a filename that arrives base64- or multipart-encoded and is decoded by application code, or a second proxy hop that does not normalise — because then ../ does reach the pathname constructor and the resolved path leaves the restricted directory, which is exactly the CWE-22 condition.
  sources: <https://cwe.mitre.org/data/definitions/22.html> · <https://portswigger.net/web-security/file-path-traversal>
- **A response whose echoed path has ./ and ../ components stripped is consistent with normalisation by the client, the server, the framework, or the terminal - it does not by itself evidence an input filter, and it is not proof the traversal failed either.**  
  `under_review` · score 0.918 · disproved by: The claim is false when the normalisation is provably server-side and effective - you can show the request as received by the origin, for example through a request log or a reflected value that only the server could have computed, and the traversal payload in that same form still fails, which is a genuine control. It is also false where the client is not in the picture at all: a request made from a script with a raw socket, a binary body carrying the path, or a file upload field bypasses any browser canonicalisation, so evidence from that channel is not subject to this ambiguity. And a genuinely successful read is a finding regardless of how many stages normalised the string on the way in, because the read happened.
  sources: <https://man7.org/linux/man-pages/man2/open.2.html> · <https://www.kernel.org/doc/html/latest/filesystems/path-lookup.html>
- **A filename you supplied appearing in a traversal error page or a session cookie is not a file read; the finding needs file CONTENT returned as the response body.**  
  `under_review` · score 0.8715 · disproved by: If the same route serves a fixed placeholder body for every nonexistent path including your traversal form, the identical-response rule applies and the report is a false positive; if any one form returns real file bytes, the finding is real regardless of what the other forms did.
  sources: <https://blog.qualys.com/vulnerabilities-threat-research/2021/10/27/apache-http-server-path-traversal-remote-code-execution-cve-2021-41773-cve-2021-42013> · <https://projectdiscovery.io/blog/nuclei-templates-april-2026>
- **A user-supplied filename joined to a base directory and then canonicalised with a platform API (realpath, Path.getCanonicalPath, GetFullPath, abs_path) whose result still begins with the expected base directory is not path traversal, because canonicalisation resolves the .. segments and symlinks and the read stays inside the restricted directory the check named.**  
  `high_confidence` · score 0.869 · disproved by: The rule is wrong when canonicalisation happens before validation rather than after (encoding introduced after the check), when the prefix test is a bare string compare so that /var/www/images_evil passes a check against /var/www/images, when the canonical base itself is attacker-influenced (a symlinked upload directory or a user-supplied base), when a TOCTOU swap replaces the validated path component before the open, or when the sink is not the filesystem but a shell, an include statement or an archive extractor that re-interprets the un-canonicalised string.
  sources: <https://cwe.mitre.org/data/definitions/22.html> · <https://portswigger.net/web-security/file-path-traversal>
- **A file-serving helper whose first argument is documented as a trusted path is not a traversal candidate, because nothing in that signature claims the caller controls it - the bug is at the call site, not in the helper.**  
  `under_review` · score 0.8105 · disproved by: The claim is false when the helper is nonetheless reached with attacker-controlled data - a handler that does new = send_file(request.args['name']) has the vulnerability regardless of what the documentation says, and the report is correct even though the blame is shared. It is also false when the path is trusted but the file it points to is not, which is a distinct and very productive finding: an attacker who can create a symlink or an archive entry inside a trusted directory escapes the directory without any traversal string at all, so no amount of argument validation would have helped. And the rule does not apply to the confined function: send_from_directory's safe_join behaviour and its 404 for a path that does not point to an existing regular file are the control, and an endpoint using it is not a traversal candidate on the argument alone.
  sources: <https://werkzeug.palletsprojects.com/en/stable/utils/> · <https://www.kernel.org/doc/html/latest/filesystems/path-lookup.html>

## Impact

- **An LFI sink is an execution primitive rather than a read primitive, so the moment it can be pointed at a file the tester controls the included content runs with the web server's privileges.**  
  `high_confidence` · score 0.808 · disproved by: Refuted if the sink returns the uploaded file's content as inert data without executing, for example because the include is downgraded to a read or the file's extension is never interpreted.
  sources: <https://man7.org/linux/man-pages/man2/open.2.html> · <https://raw.githubusercontent.com/HackTricks-wiki/hacktricks/master/src/pentesting-web/file-inclusion/lfi2rce-via-eternal-waiting.md>
- **Path traversal enables reading arbitrary files (confidentiality breach), and where the vulnerable input flows into a file include/execute primitive (PHP include, LFI, JSP/SQL), it enables code execution via log poisoning, wrapper protocols, or upload of a webshell.**  
  `high_confidence` · score 0.759 · disproved by: Run the serving process with the minimum filesystem permissions needed so even a successful traversal reaches only files the process account can read; serve files through an allowlist; replace raw paths with server-side identifiers.
  sources: <https://community.owasp.org/attacks/Path_Traversal> · <https://cwe.mitre.org/data/published/cwe_latest.pdf> · <https://safeguard.sh/resources/blog/what-is-path-traversal> · <https://www.skillsdirectory.com/skills/jeffreytse-prevent-path-traversal>

## Variant

- **Path traversal has distinct CWE variants: CWE-23 relative path traversal (parent-directory sequences), CWE-36 absolute path traversal (direct absolute paths bypass base directories entirely), and CWE-59 improper link resolution (symlink following).**  
  `high_confidence` · score 0.723 · disproved by: Reject absolute path prefixes ('/', 'C:\') as a defense-in-depth layer; prefer opaque identifiers mapped server-side; verify every archive entry name before extraction; follow the canonical path chain and resolve symlinks explicitly before asserting containment.
  sources: <https://cwe.mitre.org/data/definitions/22> · <https://cwe.mitre.org/data/published/cwe_v4.16.pdf> · <https://eligof.github.io/Web-App-Pentesting-Playbook/vulns/path-traversal.html> · <https://turingpoint.de/en/vulnerability-database/CWE-36/>

## Bypass

- **A traversal allowlist is bypassed when the filter compares the raw request path but the backend normalizes percent-encoded octets before resolving the file.**  
  `under_review` · score 0.984 · disproved by: If the percent-encoded form is rejected identically to the literal form, or if the backend serves neither variant outside the intended directory, no allowlist bypass exists and the payload is simply blocked.
  sources: <https://httpwg.org/specs/rfc9110.html> · <https://blog.qualys.com/vulnerabilities-threat-research/2021/10/27/apache-http-server-path-traversal-remote-code-execution-cve-2021-41773-cve-2021-42013>
- **Path traversal payloads are typically obfuscated to defeat simple filters: URL encoding (%2e%2e%2f), double URL encoding (%252e%252e%252f), partial encoding (..%2f), null-byte termination (%00 on legacy PHP < 5.3.4), and filter bypasses such as '....//' that survive non-recursive replacement.**  
  `high_confidence` · score 0.85 · disproved by: Canonicalize the path with realpath/getCanonicalPath/Path.resolve to an absolute path that collapses all encoding variants, then assert containment with a separator-aware comparison; reject null bytes, backslashes, and absolute-path markers as a defense-in-depth layer.
  sources: <https://desecurity.github.io/hacktricks/pentesting-web/file-inclusion/> · <https://eligof.github.io/Web-App-Pentesting-Playbook/vulns/path-traversal.html> · <https://enriquefolte.com/manual/03_Exploitation/Web_Exploitation/LFI_Path_Traversal_Bypasses> · <https://github.com/DIPRO31/NullByte-Pentest-Report>
- **Confining the resolved path under a base directory by string prefix does not contain a symbolic link, because resolving the link replaces the component and discards all preceding parts of the path when the link body is absolute.**  
  `high_confidence` · score 0.8105 · disproved by: The claim is false when the open itself is confined below the base rather than merely checked - resolving with an openat-style call relative to a directory file descriptor for the base directory, so the kernel performs component resolution with that directory as the root and cannot escape it by any path, because a '..' or an absolute link body cannot climb above the descriptor. It is also false where the service runs with a chroot, a container mount namespace, or a filesystem sandbox that makes the out-of-tree target unreadable, in which case the symlink exists but reaches nothing. And the finding needs the write: an attacker-controlled directory that is not writable gives no place to plant the link, so a report without a demonstrated link creation is a hypothesis.
  sources: <https://werkzeug.palletsprojects.com/en/stable/utils/> · <https://www.kernel.org/doc/html/latest/filesystems/path-lookup.html>
- **A local file inclusion filter that strips '../' is bypassed by re-encoding the traversal (%2e%2e%2f), because the filter matches the decoded form the request never carries.**  
  `high_confidence` · score 0.7995 · disproved by: Refuted when the server percent-decodes the parameter before filtering, in which case the encoded sequence is normalised to ../ and rejected; the bypass only exists where filtering happens on the raw, undecoded request value.
  sources: <https://portswigger.net/web-security/file-path-traversal> · <https://raw.githubusercontent.com/Esther7171/HackTheBox-Writeups-Walkthroughs/main/Write-ups/Academy/05.%20Web%20Exploitation/28.%20File%20Inclusion/File%20Inclusion.md>

## Mechanic

- **Path traversal (CWE-22) occurs when untrusted input is used to construct a file path without neutralizing special elements such as '../' that resolve outside a restricted directory.**  
  `high_confidence` · score 0.759 · disproved by: Carving off directory components with os.path.basename() or a server-side allowlist of permitted filenames, combined with canonical-path containment verification that asserts the resolved absolute path starts with the base directory.
  sources: <https://community.owasp.org/attacks/Path_Traversal> · <https://cwe.mitre.org/data/published/cwe_latest.pdf> · <https://desecurity.github.io/hacktricks/pentesting-web/file-inclusion/> · <https://eligof.github.io/Web-App-Pentesting-Playbook/vulns/path-traversal.html>

## Cve

- **High-severity path traversal CVEs in popular infrastructure include CVE-2019-19781 (Citrix ADC/Gateway), CVE-2021-41773 and CVE-2021-42013 (Apache HTTP Server 2.4.49), and CVE-2019-11510 (Pulse Secure VPN), each allowing unauthenticated arbitrary file read and, in several cases, leading to remote code execution.**  
  `high_confidence` · score 0.759 · disproved by: Patch promptly; restrict file execution in web roots; keep WAF and rule sets updated; monitor proxy logs for traversal signatures; remove unnecessary CGI modules.
  sources: <https://community.owasp.org/attacks/Path_Traversal> · <https://cwe.mitre.org/data/published/cwe_latest.pdf> · <https://safeguard.sh/resources/blog/what-is-path-traversal> · <https://www.skillsdirectory.com/skills/jeffreytse-prevent-path-traversal>

## Remediation

- **The reliable fix is canonicalization-then-containment: resolve the candidate path to an absolute canonical path (realpath, getCanonicalPath, Path.resolve) and assert it starts with the base directory plus a separator; prefer opaque identifiers mapped server-side; reject null bytes and separators as defense-in-depth.**  
  `high_confidence` · score 0.759 · disproved by: A fix is verifiable: canonicalize the joined path and compare with a separator-aware prefix match. A naive 'remove ../' blacklist is insufficient and must not be relied upon. Test the patched code with /etc/passwd, /etc/shadow, and encoded payloads.
