# Cross-Site Scripting

> surface: `client` · CWE: CWE-79 · OWASP: A03:2021
> maturity: **mature** — 70 items, 70 supported, 25 FP rules, 1 chains

Attacker-controlled data reaches a script execution context in another user's browser without neutralisation.

**Aliases:** xss, cross site scripting, stored xss, reflected xss, dom xss

## Prerequisite

- **Reflected XSS requires attacker data from the current HTTP request to be embedded unneutralized in that same immediate response.**  
  `high_confidence` · score 0.932 · disproved by: The unique probe value is absent from the immediate HTTP response for that surface, or appears only after a separate later request, making it stored rather than reflected.
  sources: <https://cwe.mitre.org/data/definitions/79.html> · <https://owasp.org/www-community/attacks/xss/> · <https://portswigger.net/web-security/cross-site-scripting/reflected>
- **Stored XSS requires the payload to persist in a server-side store and later render in another user's response, so proof needs two distinct steps.**  
  `high_confidence` · score 0.861 · disproved by: The payload executes only in the submitting user's own session and never renders for any other user or role.
  sources: <https://cwe.mitre.org/data/definitions/79.html> · <https://portswigger.net/web-security/cross-site-scripting/stored>

## Signal

- **A short unique alphanumeric marker submitted to an entry point and found verbatim in the response is the working precondition signal for reflected XSS.**  
  `high_confidence` · score 0.8885 · disproved by: The marker is absent from the response, appears only encoded in a form that cannot be decoded back into a live context, or is reflected only after a separate later request.
  sources: <https://owasp.org/www-community/attacks/xss/> · <https://portswigger.net/web-security/cross-site-scripting/reflected>
- **DOM XSS exists only where an attacker-controllable source reaches an execution-capable sink; reading the source alone is not a finding.**  
  `high_confidence` · score 0.806 · disproved by: The source is read but the value always flows into a safe sink such as textContent or setAttribute, or never reaches any execution-capable sink.
  sources: <https://cwe.mitre.org/data/definitions/79.html> · <https://portswigger.net/web-security/cross-site-scripting/dom-based>

## Technique

- **An injected unclosed attribute makes the browser send the rest of the response to an attacker URL, achieving data capture with no script execution.**  
  `high_confidence` · score 0.9325 · disproved by: This is wrong if the application escapes or filters the quote and angle-bracket characters that the breakout requires, or if no sensitive data follows the injection point in the response.
  sources: <https://cwe.mitre.org/data/definitions/79.html> · <https://portswigger.net/web-security/cross-site-scripting/dangling-markup>
- **DOM-based XSS exists only where an attacker-controllable source reaches a sink that supports dynamic code execution.**  
  `high_confidence` · score 0.9325 · disproved by: This is wrong if the source is read but its value only ever reaches a safe sink such as textContent or setAttribute, or never reaches any execution-capable sink.
  sources: <https://portswigger.net/web-security/cross-site-scripting/dom-based> · <https://cheatsheetseries.owasp.org/cheatsheets/DOM_based_XSS_Prevention_Cheat_Sheet.html>
- **Inside a quoted JavaScript string literal the payload must both escape the string delimiter and repair the trailing script, because any syntax error prevents execution.**  
  `high_confidence` · score 0.905 · disproved by: This is wrong if the application escapes the delimiter so the string cannot be terminated, or if the value is placed in a context that is not a string literal at all.
  sources: <https://portswigger.net/web-security/cross-site-scripting/contexts> · <https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html>
- **An application that backslash-escapes quotes without escaping the backslash itself is bypassed by prefixing the payload with its own backslash.**  
  `high_confidence` · score 0.905 · disproved by: This is wrong if the application escapes backslashes first, or uses a vetted encoder or JSON serialiser for the value, in which case the attacker's backslash is itself escaped.

  `high_confidence` · score 0.8775 · disproved by: This is wrong if the sink is document.write rather than innerHTML, if the browser is one that still runs script elements assigned via innerHTML, or if a separate code path appends the node and executes it.

  `high_confidence` · score 0.8775 · disproved by: This is wrong if the value reaching the sink is sanitised by a vetted library configured for that sink, or is only ever assigned as a property value that the browser does not parse as markup.
  sources: <https://portswigger.net/web-security/cross-site-scripting/dom-based> · <https://cheatsheetseries.owasp.org/cheatsheets/DOM_based_XSS_Prevention_Cheat_Sheet.html>
- **The URL is the most common DOM XSS source, and the payload can ride in the query string, the fragment, or the path.**  
  `high_confidence` · score 0.8775 · disproved by: This is wrong if the application reads the location and immediately decodes or strips it before any use, or if the page never passes the value into a sink that renders or executes it.

## Test

- **A payload only counts as XSS once a real browser parses the delivered page and the injected JavaScript actually runs; a payload visible in Repeater's response pane is unexecuted source text, not a finding.**  
  `high_confidence` · score 0.968 · disproved by: The procedure is wrong if a payload executes with no visible trace you chose to look for - e.g. the proof writes to a network beacon instead of the DOM, so 'no alert' reads as failure when execution actually happened. It is also wrong to require a visible popup as the sole gate: CSP report-only mode, Trusted Types default policies, and headless profiles can all suppress alert() while script still runs. Confirm with a second, independent observable (network egress, DOM mutation, console log) before calling it a failure.
  sources: <https://cwe.mitre.org/data/definitions/79.html> · <https://portswigger.net/web-security/cross-site-scripting/exploiting> · <https://portswigger.net/web-security/cross-site-scripting/reflected>
- **A short unique alphanumeric marker echoed verbatim in the response, from every request-controlled entry point tested one at a time, is the pass condition that proves reflection exists before any payload is chosen.**  
  `high_confidence` · score 0.952 · disproved by: The procedure is wrong if the marker reflects yet no XSS is reachable - that is a real possibility the method cannot detect: the reflection may sit inside a comment, inside an HTML entity-encoded attribute the app later re-decodes and re-renders on another page, or inside a JSON field that a second script writes into innerHTML on a different route. It is also wrong if the 'static string' control is insufficient, because an app that echoes a per-session value (a CSRF token built from your marker, a request-id cache) will pass step 4 and still tell you nothing about general reflection.
  sources: <https://cwe.mitre.org/data/definitions/79.html> · <https://portswigger.net/web-security/cross-site-scripting/reflected>
- **Stored XSS is proven only by storing a payload as one identity and loading the exit point as a second identity, because your own session re-rendering your own input proves storage and reflection, never cross-user execution.**  
  `high_confidence` · score 0.952 · disproved by: The procedure is wrong if you only ever test with one account and the app renders stored values differently per role - the marker may be HTML-encoded for the author and injected raw into an admin moderation queue, so your own view can look safe while the privileged view is exploitable. It is also wrong where stored data is overwritten before any second read (recent-searches lists, ephemeral carts); a marker found once is not proof of durable storage - re-read the exit point after an unrelated action to confirm it survives.
  sources: <https://owasp.org/www-community/attacks/xss/> · <https://portswigger.net/web-security/cross-site-scripting/stored>
- **Reading the characters immediately before and after each reflection point tells you which of the six XSS contexts you are in, and the context selects the payload family, so no payload should be tried before the context is named.**  
  `high_confidence` · score 0.9485 · disproved by: The procedure is wrong if a single reflection is genuinely multi-context - the same marker echoed into a hidden input AND an inline script AND a data attribute - because naming one context hides the others; you must enumerate every offset, not the first one found. It is also wrong where the payload family is chosen but the surrounding markup makes it inert: a marker inside a <title>, inside an HTML comment, inside a <textarea>, or inside an already-escaped attribute with no decode step later. Those require a different escape, not a context-specific payload.
  sources: <https://portswigger.net/web-security/cross-site-scripting/contexts> · <https://portswigger.net/web-security/cross-site-scripting/reflected> · <https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html>
- **Before writing an impact claim, read the live response headers for the CSP nonce/hash/strict-dynamic directives, the HttpOnly flag on the session cookie, and any require-trusted-types-for directive, because each one caps what your confirmed execution can actually do.**  
  `high_confidence` · score 0.9485 · disproved by: The procedure is wrong if you treat a nonce you observed on one page load as a permanent value and paste it into a payload - a nonce is regenerated per response, so a captured nonce will not match and the test fails for the wrong reason. It is also wrong to conclude a control blocks impact from the header alone: nonce/hash/strict-dynamic govern script execution, not already-confirmed event-handler execution through a parsed HTML node in every policy, and HttpOnly says nothing about tokens held in localStorage.
  sources: <https://portswigger.net/web-security/cross-site-scripting/content-security-policy> · <https://portswigger.net/web-security/cross-site-scripting/exploiting> · <https://cheatsheetseries.owasp.org/cheatsheets/Content_Security_Policy_Cheat_Sheet.html> · <https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html> · <https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html> · <https://developer.mozilla.org/en-US/docs/Web/API/Trusted_Types_API>
- **When a filter blocks parentheses you switch to a parentheses-free invocation, and when the reflection lands inside backticks you use ${...} with no terminator at all - both are determined by what step 1 showed you in the response.**  
  `high_confidence` · score 0.94 · disproved by: The procedure is wrong if the marker lands in a template literal that is never actually evaluated as a tagged/interpolated expression at runtime (a string built for display, or a literal inside a JSON blob parsed as data) - ${...} then stays literal text and you will have burned the window on the wrong technique. It is also wrong to assume parentheses-free invocation survives everywhere: onerror=alert;throw 1 needs an element that fires error, so on a non-error context the payload is inert and the miss is a context error, not proof the filter holds.
  sources: <https://cwe.mitre.org/data/definitions/79.html> · <https://portswigger.net/web-security/cross-site-scripting/contexts> · <https://cheatsheetseries.owasp.org/cheatsheets/XSS_Filter_Evasion_Cheat_Sheet.html>
- **For DOM XSS you must seed the marker into a client-side source such as location.search and locate it in the live DOM with devtools Control+F, because the browser's View Source never shows JavaScript-injected nodes.**  
  `high_confidence` · score 0.8775 · disproved by: The procedure is wrong if the app renders the marker only after an interaction or a timer - a click, a scroll, a setTimeout, a route change - because a single load-time Control+F finds nothing and the source IS reachable. It is also wrong where the value is passed to an execution sink such as eval or setTimeout-with-string, where the marker legitimately never appears in the DOM, so 'absent from the DOM' is not evidence of safety and must not be recorded as a clean result.
  sources: <https://portswigger.net/web-security/cross-site-scripting/dom-based> · <https://cheatsheetseries.owasp.org/cheatsheets/HTML5_Security_Cheat_Sheet.html>
- **When a filter blocks your quote or tag characters, probe the decoder gap in a fixed order - HTML-entity-encode the blocked character first, then prepend a backslash to neutralise the app's own escaping - and a hit proves the filter normalises but does not neutralise.**  
  `high_confidence` · score 0.869 · disproved by: The procedure is wrong if the entity probe is fired at the wrong layer: &#39; only helps where the browser HTML-decodes before parsing, so sending it into a JS string inside a <script> block, into a URL, or into a CSS value does nothing, and a hunter who treats a non-firing entity probe as proof of safety has only tested one decoder. It is also wrong to stop at the first working bypass - the same filter may have a second gap, and reporting only the first understates the defect.
  sources: <https://portswigger.net/web-security/cross-site-scripting/contexts> · <https://cheatsheetseries.owasp.org/cheatsheets/XSS_Filter_Evasion_Cheat_Sheet.html>
- **Grepping a downloaded JS bundle for the concrete sink token set - innerHTML, outerHTML, insertAdjacentHTML, document.write/writeln, eval, new Function, setTimeout/setInterval with a string first argument, and the jQuery html/append family - is what converts 'this page uses innerHTML somewhere' into a list of lines you can actually test.**  
  `high_confidence` · score 0.866 · disproved by: The procedure is wrong if the sink token appears in dead code, a comment, a minifier artifact, or an error-handling branch that never runs - a raw grep hit is a candidate list, not a vulnerability, and a hit list with no reachability analysis will generate false positives. It is also wrong as a completeness claim: many apps reach sinks through a framework abstraction (a template engine's {{{ }}} escape, a v-html directive, React's dangerouslySetInnerHTML) where the literal token never appears in any bundle.
  sources: <https://portswigger.net/web-security/cross-site-scripting/dom-based> · <https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html> · <https://cheatsheetseries.owasp.org/cheatsheets/DOM_based_XSS_Prevention_Cheat_Sheet.html>
- **A DOM XSS claim is only proven when the debugger shows an actual value flowing from a source read into an execution sink, because grepping source and sink names separately proves nothing about the path between them.**  
  `high_confidence` · score 0.814 · disproved by: The procedure is wrong if the path is data-dependent and your single marker run takes a different branch than the attacker's input would (a length check, an if/else on the first character, a try/catch). A clean debugger trace on one marker does not prove the branch an attacker's payload would take is also safe. It is also wrong to stop at the first sink: a value often flows into a safe sink AND an unsafe sink, so the trace must continue to every use of the tainted variable.
  sources: <https://portswigger.net/web-security/cross-site-scripting/dom-based> · <https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html>

## Validation

- **A payload that fires an alert only in the hunter's own browser demonstrates script execution but not a reportable vulnerability, because impact requires the payload to reach another user's session or a reachable victim path.**  
  `high_confidence` · score 0.921 · disproved by: If the payload demonstrably renders and executes in a second, independently authenticated session or in a view reached by another user, then the marker is not self-only and the finding does clear the bar.
  sources: <https://portswigger.net/web-security/cross-site-scripting> · <https://portswigger.net/web-security/cross-site-scripting/exploiting> · <https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html>
- **An escape routine that is correct for one context does not protect another, so a finding is wrong until the encoding is shown to match the exact context the value lands in.**  
  `high_confidence` · score 0.8775 · disproved by: This is wrong if the value is context-correctly encoded by a vetted encoder for its exact destination, or if it is inserted as a property value on a sink that encodes automatically.
  sources: <https://portswigger.net/web-security/cross-site-scripting/contexts> · <https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html>
- **If a DOM source value is URL-encoded before reaching the sink the markup payload cannot survive, making the candidate a false positive.**  
  `high_confidence` · score 0.8415 · disproved by: A non-encoded payload with no percent sequences in the traced value reaches the sink and executes script in the victim's browser.
  sources: <https://portswigger.net/web-security/cross-site-scripting/dom-based> · <https://cheatsheetseries.owasp.org/cheatsheets/DOM_based_XSS_Prevention_Cheat_Sheet.html>
- **An HttpOnly session cookie removes the cookie-exfiltration chain, so impact must be restated as in-origin actions rather than session theft.**  
  `high_confidence` · score 0.8415 · disproved by: The session cookie lacks HttpOnly and document.cookie returns it inside the injected script, so full session replay is achievable.
  sources: <https://portswigger.net/web-security/cross-site-scripting/exploiting> · <https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html>
- **A page that handles postMessage without validating event.origin accepts attacker-controlled input from any origin.**  
  `high_confidence` · score 0.784 · disproved by: This is wrong if the handler verifies event.origin against an exact expected origin before acting, or if the data is only used in a context that cannot reach a sink or a privileged action.
  sources: <https://cheatsheetseries.owasp.org/cheatsheets/HTML5_Security_Cheat_Sheet.html> · <https://developer.mozilla.org/en-US/docs/Web/API/Window/postMessage>

## Fp Rule

- **Reject a report's 'steals session cookies' impact claim when the session cookie carries the HttpOnly attribute, and restate the impact as in-origin action on behalf of the victim instead.**  
  `high_confidence` · score 0.96 · disproved by: The rule is wrong if the session cookie lacks HttpOnly and document.cookie returns it to injected script, in which case full session replay IS achievable and the original impact claim stands. It is also wrong when the sensitive credential is not the cookie at all - a JWT or API token in localStorage or sessionStorage, or a CSRF token readable from the DOM, is unaffected by HttpOnly. Read the Session Management cheat sheet's own warning before assuming HttpOnly helps: it only protects the confidentiality of that one cookie.
  sources: <https://portswigger.net/web-security/cross-site-scripting/exploiting> · <https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html>
- **Reject a JSON API endpoint reported as XSS when the response Content-Type is application/json and no client-side code path inserts the reflected value into an HTML document.**  
  `high_confidence` · score 0.96 · disproved by: The rule is wrong if the same reflected value reaches an HTML-executing context through any code path: the API is called by a front end that assigns the response into innerHTML or a framework's raw-HTML binding, the endpoint is reachable at the same path with a text/html or JSONP callback content type, or the server renders the stored value into an HTML page for other users. Then the JSON body is only the delivery mechanism, and the finding is a genuine XSS located at the sink.
  sources: <https://portswigger.net/web-security/cross-site-scripting> · <https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html>
- **Reject a reflected XSS candidate when the reflected value appears in the response only as HTML entities or percent/unicode escapes that the browser decodes back to inert text in that context, because encoding is what makes the reflection non-exploitable.**  
  `high_confidence` · score 0.952 · disproved by: The rule is wrong if the encoding is applied for the wrong context - for example only HTML-entity-encoded output dropped inside a JavaScript string, a URL, a CSS value or an unquoted attribute, where &quot; and &#39; do not neutralise a quote delimiter and a ';alert(1)// payload still breaks the string. It is also wrong if the entity is decoded and re-serialised anywhere before rendering (a client-side read of .innerHTML followed by a re-write, or a client-side template that re-interprets the text as HTML), because then the inert text becomes live markup.
  sources: <https://cwe.mitre.org/data/definitions/79.html> · <https://portswigger.net/web-security/cross-site-scripting/contexts>
- **Reject an XSS candidate as unproven when the payload can only be made to render by pasting attacker-supplied JavaScript into the submitter's own address bar or console, because that is self-XSS and not a cross-user finding.**  
  `high_confidence` · score 0.952 · disproved by: The candidate stops being self-XSS the moment a working delivery exists: a crafted URL (or a CSRF-style auto-submitting form) that fires the payload automatically in any other user's browser, on a page an authenticated victim visits. Then it is ordinary reflected XSS and this rejection rule is wrong. Equally, if the 'pasting' step is not required because the value is stored and later rendered to other users, the finding is stored XSS, not self-XSS.
  sources: <https://cwe.mitre.org/data/definitions/79.html> · <https://portswigger.net/web-security/cross-site-scripting/reflected>
- **Reject a DOM or reflected XSS candidate when the live page ships a CSP whose script-src carries a nonce or hash source without unsafe-inline and without strict-dynamic, because your injected inline script and inline event handlers cannot execute.**  
  `high_confidence` · score 0.9325 · disproved by: The rule is wrong when the policy contains 'unsafe-inline' (or 'unsafe-eval' for eval-style payloads), or when strict-dynamic is present and the injection point runs on a page that already loaded a nonced/hash-trusted script - in both cases a nonce-less injected script is executed anyway and the finding is a full XSS. It is also wrong if the CSP is only a report-only header (Content-Security-Policy-Report-Only), which logs violations without blocking anything.
  sources: <https://portswigger.net/web-security/cross-site-scripting/content-security-policy> · <https://cheatsheetseries.owasp.org/cheatsheets/Content_Security_Policy_Cheat_Sheet.html>
- **Reject a stored XSS candidate when the submitted payload never appears in any response served to another user or role, because a store-only write with no second-user render is not cross-site script execution.**

## Evidence

  `high_confidence` · score 0.9325 · disproved by: The claim is wrong if the site does not reflect any input into the policy, since there is then nothing to inject and the nonce stands. It is also wrong if the reflected value is filtered so a semicolon or a comma cannot appear, because then no new directive can be opened. It is wrong for browsers that do not implement script-src-elem, where an appended script-src would simply be dropped as a duplicate and the original policy would still apply. And it is wrong where Trusted Types enforcement is on and the assignment throws before any parsing happens.

  `high_confidence` · score 0.8475 · disproved by: The claim is wrong if the config object defines its own transport_url property, because an object's own property takes precedence over anything inherited from the prototype and the gadget cannot fire.   `high_confidence` · score 0.8115 · disproved by: The claim is wrong if a default policy is defined and its transformation function returns the input unchanged, for example a policy built with DOMPurify replaced by an identity function - the sink then receives a TrustedScript and the exception never fires. ## False-positive rules

- **Hypothesis:** GET /search returns the q parameter unencoded in the HTML body
  - **Invalidated by:** The response was served as application/json and the page inserted it via textContent, so the injected markup was parsed as text and never became nodes
  - **Rule:** Reflection is not execution: confirm the response is parsed as HTML and that the value reaches an execution-capable sink before calling it XSS

- **Hypothesis:** Cookie theft via reflected XSS on an authenticated settings page
  - **Invalidated by:** The session cookie carried HttpOnly, so document.cookie returned nothing — but the script could still read the page's CSRF token and submit the password change with it, which is the real impact
  - **Rule:** Never price XSS as cookie theft until you read the cookie flags; with HttpOnly the finding is in-origin privileged action, which is usually higher impact anyway

- **Hypothesis:** Reject a report's 'steals session cookies' impact claim when the session cookie carries the HttpOnly attribute, and restate the impact as in-origin action on behalf of the victim instead.
  - **Invalidated by:** The rule is wrong if the session cookie lacks HttpOnly and document.cookie returns it to injected script, in which case full session replay IS achievable and the original impact claim stands. It is also wrong when the sensitive credential is not the cookie at all - a JWT or API token in localStorage or sessionStorage, or a CSRF token readable from the DOM, is unaffected by HttpOnly. Read the Session Management cheat sheet's own warning before assuming HttpOnly helps: it only protects the confidentiality of that one cookie.
  - **Rule:** Reject a report's 'steals session cookies' impact claim when the session cookie carries the HttpOnly attribute, and restate the impact as in-origin action on behalf of the victim instead.

- **Hypothesis:** Reject a DOM or reflected XSS candidate when the live page ships a CSP whose script-src carries a nonce or hash source without unsafe-inline and without strict-dynamic, because your injected inline script and inline event handlers cannot execute.
  - **Invalidated by:** The rule is wrong when the policy contains 'unsafe-inline' (or 'unsafe-eval' for eval-style payloads), or when strict-dynamic is present and the injection point runs on a page that already loaded a nonced/hash-trusted script - in both cases a nonce-less injected script is executed anyway and the finding is a full XSS.   - **Rule:** Reject an XSS candidate as unproven when the payload can only be made to render by pasting attacker-supplied JavaScript into the submitter's own address bar or console, because that is self-XSS and not a cross-user finding.

- **Hypothesis:** Reject a DOM-based XSS candidate when the traced attacker-controlled source only ever reaches textContent, innerText, or setAttribute with a hardcoded non-event attribute, because those sinks treat the value as text and never parse it as markup.
  - **Invalidated by:** The candidate is a real DOM XSS if the identical tainted value, in the identical code path, is also passed to an execution-capable sink - innerHTML/outerHTML/insertAdjacentHTML/document.write/eval/string setTimeout - anywhere the same value can reach on another page load, in a fallback branch, or for a different input shape. This rule is also wrong if setAttribute's attribute NAME is derived from the same tainted input (setAttribute(t, v) where t is user-influenced), because OWASP limits setAttribute's safety to hardcoded, innocuous attribute names; an injected name such as onmouseover re-creates an injection sink.
  - **Rule:** Reject a DOM-based XSS candidate when the traced attacker-controlled source only ever reaches textContent, innerText, or setAttribute with a hardcoded non-event attribute, because those sinks treat the value as text and never parse it as markup.

- **Hypothesis:** Reject a stored XSS candidate when the submitted payload never appears in any response served to another user or role, because a store-only write with no second-user render is not cross-site script execution.
  - **Invalidated by:** The rule is wrong if any second surface renders the stored value - an admin moderation queue, a different user's listing or profile page, a notification email, an export/CSV/PDF generator, a webhook payload or a third-party integration that re-renders the string as HTML. Any one of those makes it genuine stored XSS, because the hunter now has two distinct steps: store, then a second user's response executes it.
  - **Rule:** Reject a stored XSS candidate when the submitted payload never appears in any response served to another user or role, because a store-only write with no second-user render is not cross-site script execution.
