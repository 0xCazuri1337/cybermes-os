# Cross-Site Scripting

> surface: `client` · CWE: CWE-79 · OWASP: A03:2021
> maturity: **mature** — 114 items, 74 supported, 22 FP rules, 1 chains

Attacker-controlled data reaches a script execution context in another user's browser without neutralisation.

**Aliases:** xss, cross site scripting, stored xss, reflected xss, dom xss

## Prerequisite

- **Reflected XSS requires attacker data from the current HTTP request to be embedded unneutralized in that same immediate response.**  
  `high_confidence` · score 0.932 · disproved by: The unique probe value is absent from the immediate HTTP response for that surface, or appears only after a separate later request, making it stored rather than reflected.
  sources: <https://cwe.mitre.org/data/definitions/79.html> · <https://owasp.org/www-community/attacks/xss/> · <https://portswigger.net/web-security/cross-site-scripting/reflected>
- **Stored XSS requires the payload to persist in a server-side store and later render in another user's response, so proof needs two distinct steps.**  
  `high_confidence` · score 0.861 · disproved by: The payload executes only in the submitting user's own session and never renders for any other user or role.
  sources: <https://cwe.mitre.org/data/definitions/79.html> · <https://portswigger.net/web-security/cross-site-scripting/stored>
- **Service-worker XSS is only reachable when two prerequisites line up: a place to serve attacker JavaScript from the target origin, either a file upload or a JSONP endpoint whose output can be filled with arbitrary JS, plus an XSS that can load and register that script as the worker.**  
  `high_confidence` · score 0.8255 · disproved by: Registering and controlling a worker script on the origin with neither arbitrary-JS hosting nor a JSONP endpoint that can be made to emit arbitrary JS refutes these as the required prerequisites.
  sources: <https://portswigger.net/web-security/cross-site-scripting/dom-based> · <https://raw.githubusercontent.com/HackTricks-wiki/hacktricks/master/src/pentesting-web/xss-cross-site-scripting/abusing-service-workers.md>
- **An onerror-style inline event handler payload only runs when script-src actually permits inline execution, so the extension CSP has to be read before the payload is called exploitable — 'unsafe-eval' in the policy buys the tester nothing here.**  
  `high_confidence` · score 0.8255 · disproved by: An inline event handler payload firing on a page whose script-src carries only 'unsafe-eval', with no 'unsafe-inline', no matching hash or nonce, and no other executable gadget, refutes this gating.
  sources: <https://portswigger.net/web-security/cross-site-scripting/contexts> · <https://raw.githubusercontent.com/HackTricks-wiki/hacktricks/master/src/pentesting-web/browser-extension-pentesting-methodology/browext-xss-example.md>
- **The worker body is the delivery half of the chain: a fetch-event listener that forwards every intercepted request URL off-origin only runs if that script is served from the vulnerable origin, so both the upload path and the JSONP path are worth probing for a real XSS.**  
  `high_confidence` · score 0.8255 · disproved by: A fetch-listener worker registered and intercepting traffic from a script hosted off the vulnerable origin, or a JSONP response whose callback cannot be broken out of, refutes the origin-delivery requirement.
  sources: <https://portswigger.net/web-security/cross-site-scripting/dom-based> · <https://raw.githubusercontent.com/HackTricks-wiki/hacktricks/master/src/pentesting-web/xss-cross-site-scripting/abusing-service-workers.md>
- **An injection-class report stands only when untrusted input is shown reaching an interpreter that acts on it, and for cross-site scripting that interpreter is the browser executing a script, event handler or DOM write rather than text rendered inert.**  
  `high_confidence` · score 0.814 · disproved by: If the same input is provably neutralised by encoding or escaping before it reaches any browser-executed script context, event handler or DOM write, the cross-site scripting claim fails.
  sources: <https://owasp.org/www-community/attacks/xss/> · <https://portswigger.net/web-security/cross-site-scripting/contexts> · <https://oreobiscuit.gitbook.io/introduction/bug-bounty-reports-and-articles/injections-html-xss-etc.md>
- **A message listener that never checks the origin of incoming messages turns cross-origin postMessage data into a cross-site scripting vector, because any hostile page can then drive the handler.**  
  `under_review` · score 0.814 · disproved by: A handler that rejects messages whose origin is not the expected one, and never writes the received data into a scriptable sink, is not reachable cross-origin.
  sources: <https://owasp.org/www-community/attacks/xss/> · <https://portswigger.net/web-security/cross-site-scripting/content-security-policy> · <https://kathan19.gitbook.io/howtohunt/xss/post_message_xss.md>

## Signal

- **A short unique alphanumeric marker submitted to an entry point and found verbatim in the response is the working precondition signal for reflected XSS.**  
  `under_review` · score 0.8885 · disproved by: The marker is absent from the response, appears only encoded in a form that cannot be decoded back into a live context, or is reflected only after a separate later request.
  sources: <https://owasp.org/www-community/attacks/xss/> · <https://portswigger.net/web-security/cross-site-scripting/reflected>
- **Reflection alone is not a cross-site scripting finding when the reflected payload sits in the body of a 302: the browser never renders that body, so the injection only counts once it lands somewhere the browser actually parses.**  
  `high_confidence` · score 0.8255 · disproved by: Script executing from a payload delivered only in the body of a 302 response, in a browser that follows the redirect before parsing, refutes this claim.
  sources: <https://portswigger.net/web-security/cross-site-scripting/content-security-policy> · <https://raw.githubusercontent.com/HackTricks-wiki/hacktricks/master/src/pentesting-web/xss-cross-site-scripting/README.md>
- **DOM XSS exists only where an attacker-controllable source reaches an execution-capable sink; reading the source alone is not a finding.**  
  `high_confidence` · score 0.806 · disproved by: The source is read but the value always flows into a safe sink such as textContent or setAttribute, or never reaches any execution-capable sink.
  sources: <https://cwe.mitre.org/data/definitions/79.html> · <https://portswigger.net/web-security/cross-site-scripting/dom-based>
- **The XSS sink to hunt for in extension code is the pattern of reading a value out of an input, concatenating it into an HTML string and appending the result to the DOM, because that route is open even where the extension CSP blocks eval-like and inline script execution.**  
  `high_confidence` · score 0.798 · disproved by: A concatenating handler whose value is escaped or inserted as text before the append, so the same input renders as literal characters with no new element or handler, refutes this sink pattern.
  sources: <https://portswigger.net/web-security/cross-site-scripting/contexts> · <https://raw.githubusercontent.com/HackTricks-wiki/hacktricks/master/src/pentesting-web/browser-extension-pentesting-methodology/browext-xss-example.md>

## Technique

- **An injected unclosed attribute makes the browser send the rest of the response to an attacker URL, achieving data capture with no script execution.**  
  `high_confidence` · score 0.9325 · disproved by: This is wrong if the application escapes or filters the quote and angle-bracket characters that the breakout requires, or if no sensitive data follows the injection point in the response.
  sources: <https://cwe.mitre.org/data/definitions/79.html> · <https://portswigger.net/web-security/cross-site-scripting/dangling-markup>
- **DOM-based XSS exists only where an attacker-controllable source reaches a sink that supports dynamic code execution.**  
  `under_review` · score 0.9325 · disproved by: This is wrong if the source is read but its value only ever reaches a safe sink such as textContent or setAttribute, or never reaches any execution-capable sink.
  sources: <https://portswigger.net/web-security/cross-site-scripting/dom-based> · <https://cheatsheetseries.owasp.org/cheatsheets/DOM_based_XSS_Prevention_Cheat_Sheet.html>
- **Inside a quoted JavaScript string literal the payload must both escape the string delimiter and repair the trailing script, because any syntax error prevents execution.**  
  `under_review` · score 0.897 · disproved by: This is wrong if the application escapes the delimiter so the string cannot be terminated, or if the value is placed in a context that is not a string literal at all.
  sources: <https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html> · <https://portswigger.net/web-security/cross-site-scripting/contexts>
- **An application that backslash-escapes quotes without escaping the backslash itself is bypassed by prefixing the payload with its own backslash.**  
  `high_confidence` · score 0.897 · disproved by: This is wrong if the application escapes backslashes first, or uses a vetted encoder or JSON serialiser for the value, in which case the attacker's backslash is itself escaped.
  sources: <https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html> · <https://portswigger.net/web-security/cross-site-scripting/contexts>
- **A JSON response served as text/html and interpolated into a page becomes an HTML injection point even though the body is JSON.**  
  `high_confidence` · score 0.8885 · disproved by: The endpoint returns application/json and no code path inserts the response body into an HTML document, so injected markup is never parsed as markup.
  sources: <https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html> · <https://portswigger.net/web-security/cross-site-scripting>
- **Stored XSS in collaborative content (wiki, issue tracker, customer ticket, comment, label color, tag) is delivered to every viewer, and when a privileged user views it the payload runs in the privileged session.**  
  `high_confidence` · score 0.885 · disproved by: Refuted if the field sanitizes style/svg/math and the diagram renderer is sandboxed, or if privileged users are exempt from the render path.
  sources: <https://owasp.org/www-community/attacks/xss/> · <https://portswigger.net/web-security/cross-site-scripting/stored> · <https://portswigger.net/web-security/cross-site-scripting/cheat-sheet>
- **Self-XSS that harms only the attacker's own session becomes effective stored XSS and account takeover when combined with a CSRF-vulnerable field mutation endpoint.**  
  `high_confidence` · score 0.885 · disproved by: Refuted if the mutation endpoint enforces a CSRF token, SameSite=Lax/Strict cookies are required, or the field is not stored and rendered.
  sources: <https://owasp.org/www-community/attacks/xss/> · <https://portswigger.net/web-security/cross-site-scripting> · <https://portswigger.net/web-security/csrf>
- **An innerHTML sink will not execute an injected script element, so execution requires an event-handler element such as img or iframe.**  
  `under_review` · score 0.8775 · disproved by: This is wrong if the sink is document.write rather than innerHTML, if the browser is one that still runs script elements assigned via innerHTML, or if a separate code path appends the node and executes it.
  sources: <https://portswigger.net/web-security/cross-site-scripting/dom-based> · <https://cheatsheetseries.owasp.org/cheatsheets/DOM_based_XSS_Prevention_Cheat_Sheet.html>
- **document.write, innerHTML, outerHTML, insertAdjacentHTML and jQuery html() are execution-capable sinks, while textContent is not.**  
  `under_review` · score 0.8775 · disproved by: This is wrong if the value reaching the sink is sanitised by a vetted library configured for that sink, or is only ever assigned as a property value that the browser does not parse as markup.
  sources: <https://portswigger.net/web-security/cross-site-scripting/dom-based> · <https://cheatsheetseries.owasp.org/cheatsheets/DOM_based_XSS_Prevention_Cheat_Sheet.html>
- **The URL is the most common DOM XSS source, and the payload can ride in the query string, the fragment, or the path.**  
  `under_review` · score 0.8775 · disproved by: This is wrong if the application reads the location and immediately decodes or strips it before any use, or if the page never passes the value into a sink that renders or executes it.
  sources: <https://portswigger.net/web-security/cross-site-scripting/dom-based> · <https://cheatsheetseries.owasp.org/cheatsheets/DOM_based_XSS_Prevention_Cheat_Sheet.html>
- **An href attribute value is already a script-capable context, so a javascript: pseudo-protocol executes script without terminating the attribute at all.**  
  `high_confidence` · score 0.8695 · disproved by: This is wrong if the application URL-encodes the value so the scheme is no longer at the start of the attribute, strips javascript: case-insensitively, or the attribute is rendered inert with no user interaction possible.
  sources: <https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html> · <https://portswigger.net/web-security/cross-site-scripting/contexts>
- **In the HTML body context the payload must introduce entirely new tags, because the reflection point has no existing quote or delimiter to escape.**  
  `high_confidence` · score 0.861 · disproved by: This is wrong if the response is not parsed as HTML at all — for example the endpoint returns application/json and nothing inserts the body into a document — or if every introduced tag is stripped or its event handler neutralised.
  sources: <https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html> · <https://portswigger.net/web-security/cross-site-scripting/contexts>
- **Injected markup with an id or name attribute creates a window/document property that shadows built-in APIs, turning attacker markup into a live configuration object.**  
  `under_review` · score 0.85 · disproved by: This is wrong if the page never reads the clobbered property, if the injected markup cannot set an id or name attribute in that position, or if the code uses getElementById or a scoped lookup that bypasses named property access.
  sources: <https://portswigger.net/web-security/cross-site-scripting/dom-based> · <https://cheatsheetseries.owasp.org/cheatsheets/DOM_Clobbering_Prevention_Cheat_Sheet.html>
- **A reflected or stored cross-site scripting entry point is confirmed when a chosen script payload executes in the page context rather than being escaped into inert text.**  
  `high_confidence` · score 0.8455 · disproved by: Refuted when the payload is returned HTML-encoded with no executable sink, which shows the output is contextually escaped rather than vulnerable.
  sources: <https://cwe.mitre.org/data/definitions/79.html> · <https://portswigger.net/web-security/cross-site-scripting> · <https://raw.githubusercontent.com/Esther7171/HackTheBox-Writeups-Walkthroughs/main/Write-ups/Academy/05.%20Web%20Exploitation/27.%20Cross-Site%20Scripting%20%28XSS%29/Cross-Site%20Scripting%20%28XSS%29.md>
- **XSS can cause a variety of problems for the end user that range in severity from an annoyance to complete account compromise.**  
  `high_confidence` · score 0.841 · disproved by: Refuted when: the same behaviour is absent when the single named control in the claim is present, and the control is shown to be present rather than assumed. Settle it by running the identical request with and without that one control and diffing the response -- if the difference the claim predicts does not appear, the claim is false. Specifically, this is refuted if the behaviour described (“XSS can cause a variety of problems for the end user that range in severity from”) does not occur under a test that isolates that control.
  sources: <https://cwe.mitre.org/data/definitions/79.html> · <https://owasp.org/www-community/attacks/xss/> · <https://portswigger.net/web-security/cross-site-scripting>
- **In an HTML attribute-value context, terminating the value and adding an event-handler attribute executes script even when angle brackets are blocked.**  
  `high_confidence` · score 0.8335 · disproved by: The quote is escaped or the value re-quoted so no additional attribute can be injected, or a strict CSP blocks inline event handlers outright.
  sources: <https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html> · <https://portswigger.net/web-security/cross-site-scripting/contexts>
- **Closing an enclosing script tag works because the browser parses HTML before JavaScript, so the injected script is parsed and executed even though the original script is left broken.**  
  `high_confidence` · score 0.8335 · disproved by: This is wrong if the application escapes the closing sequence so the script tag cannot be terminated, or if the value sits inside an external JS file rather than inline HTML, where the browser never re-parses it as markup.
  sources: <https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html> · <https://portswigger.net/web-security/cross-site-scripting/contexts>
- **When reflected data is placed inside a script block, terminating the script element is enough to get an event handler out of it, so escaping single quotes in that context buys nothing and the tester should probe the script context rather than the quoted string.**  
  `high_confidence` · score 0.8255 · disproved by: A reflected value containing a closing script tag sequence that neither terminates the block nor produces any new element or handler in the rendered page refutes the escapability.
  sources: <https://portswigger.net/web-security/cross-site-scripting/content-security-policy> · <https://raw.githubusercontent.com/HackTricks-wiki/hacktricks/master/src/pentesting-web/xss-cross-site-scripting/README.md>
- **React and Next.js SSR shift the XSS surface rather than remove it: JSX escapes string values, but server-side rendering of unescaped data plus dangerouslySetInnerHTML / url / style sinks produce XSS that client-side sanitizers cannot reach.**  
  `high_confidence` · score 0.8225 · disproved by: Never use dangerouslySetInnerHTML without sanitizing; scheme-allow-list URLs in href; sanitize style/CSS; use React's built-in escaping and CSP with script-src nonces.
  sources: <https://cheatsheetseries.owasp.org/cheatsheets/Nextjs_Security_Cheat_Sheet.html> · <https://deepstrike.io/blog/nextjs-security-testing-bug-bounty-guide> · <https://mahsamohajer.com/security>

## Test

- **A payload only counts as XSS once a real browser parses the delivered page and the injected JavaScript actually runs; a payload visible in Repeater's response pane is unexecuted source text, not a finding.**  
  `high_confidence` · score 0.968 · disproved by: The procedure is wrong if a payload executes with no visible trace you chose to look for - e.g. the proof writes to a network beacon instead of the DOM, so 'no alert' reads as failure when execution actually happened. It is also wrong to require a visible popup as the sole gate: CSP report-only mode, Trusted Types default policies, and headless profiles can all suppress alert() while script still runs. Confirm with a second, independent observable (network egress, DOM mutation, console log) before calling it a failure.
  sources: <https://cwe.mitre.org/data/definitions/79.html> · <https://portswigger.net/web-security/cross-site-scripting/exploiting> · <https://portswigger.net/web-security/cross-site-scripting/reflected>
- **A short unique alphanumeric marker echoed verbatim in the response, from every request-controlled entry point tested one at a time, is the pass condition that proves reflection exists before any payload is chosen.**  
  `high_confidence` · score 0.952 · disproved by: The procedure is wrong if the marker reflects yet no XSS is reachable - that is a real possibility the method cannot detect: the reflection may sit inside a comment, inside an HTML entity-encoded attribute the app later re-decodes and re-renders on another page, or inside a JSON field that a second script writes into innerHTML on a different route. It is also wrong if the 'static string' control is insufficient, because an app that echoes a per-session value (a CSRF token built from your marker, a request-id cache) will pass step 4 and still tell you nothing about general reflection.
  sources: <https://cwe.mitre.org/data/definitions/79.html> · <https://portswigger.net/web-security/cross-site-scripting/reflected>
- **Stored XSS is proven only by storing a payload as one identity and loading the exit point as a second identity, because your own session re-rendering your own input proves storage and reflection, never cross-user execution.**  
  `high_confidence` · score 0.952 · disproved by: The procedure is wrong if you only ever test with one account and the app renders stored values differently per role - the marker may be HTML-encoded for the author and injected raw into an admin moderation queue, so your own view can look safe while the privileged view is exploitable. It is also wrong where stored data is overwritten before any second read (recent-searches lists, ephemeral carts); a marker found once is not proof of durable storage - re-read the exit point after an unrelated action to confirm it survives.
  sources: <https://owasp.org/www-community/attacks/xss/> · <https://portswigger.net/web-security/cross-site-scripting/stored>
- **Before writing an impact claim, read the live response headers for the CSP nonce/hash/strict-dynamic directives, the HttpOnly flag on the session cookie, and any require-trusted-types-for directive, because each one caps what your confirmed execution can actually do.**  
  `under_review` · score 0.9485 · disproved by: The procedure is wrong if you treat a nonce you observed on one page load as a permanent value and paste it into a payload - a nonce is regenerated per response, so a captured nonce will not match and the test fails for the wrong reason. It is also wrong to conclude a control blocks impact from the header alone: nonce/hash/strict-dynamic govern script execution, not already-confirmed event-handler execution through a parsed HTML node in every policy, and HttpOnly says nothing about tokens held in localStorage.
  sources: <https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html> · <https://portswigger.net/web-security/cross-site-scripting/content-security-policy> · <https://portswigger.net/web-security/cross-site-scripting/exploiting> · <https://cheatsheetseries.owasp.org/cheatsheets/Content_Security_Policy_Cheat_Sheet.html> · <https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html> · <https://developer.mozilla.org/en-US/docs/Web/API/Trusted_Types_API>
- **Reading the characters immediately before and after each reflection point tells you which of the six XSS contexts you are in, and the context selects the payload family, so no payload should be tried before the context is named.**  
  `high_confidence` · score 0.9405 · disproved by: The procedure is wrong if a single reflection is genuinely multi-context - the same marker echoed into a hidden input AND an inline script AND a data attribute - because naming one context hides the others; you must enumerate every offset, not the first one found. It is also wrong where the payload family is chosen but the surrounding markup makes it inert: a marker inside a <title>, inside an HTML comment, inside a <textarea>, or inside an already-escaped attribute with no decode step later. Those require a different escape, not a context-specific payload.
  sources: <https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html> · <https://portswigger.net/web-security/cross-site-scripting/contexts> · <https://portswigger.net/web-security/cross-site-scripting/reflected>
- **When a filter blocks parentheses you switch to a parentheses-free invocation, and when the reflection lands inside backticks you use ${...} with no terminator at all - both are determined by what step 1 showed you in the response.**  
  `high_confidence` · score 0.94 · disproved by: The procedure is wrong if the marker lands in a template literal that is never actually evaluated as a tagged/interpolated expression at runtime (a string built for display, or a literal inside a JSON blob parsed as data) - ${...} then stays literal text and you will have burned the window on the wrong technique. It is also wrong to assume parentheses-free invocation survives everywhere: onerror=alert;throw 1 needs an element that fires error, so on a non-error context the payload is inert and the miss is a context error, not proof the filter holds.
  sources: <https://cwe.mitre.org/data/definitions/79.html> · <https://portswigger.net/web-security/cross-site-scripting/contexts> · <https://cheatsheetseries.owasp.org/cheatsheets/XSS_Filter_Evasion_Cheat_Sheet.html>
- **To decide this case, observe: Why it looks vulnerable: the markup injection is real - your marker sits unencoded in an HTML-executing context - so the defect is genuine even when nothing happens when the victim clicks.**

## False-positive rules

- **Hypothesis:** GET /search returns the q parameter unencoded in the HTML body
  - **Invalidated by:** The response was served as application/json and the page inserted it via textContent, so the injected markup was parsed as text and never became nodes
  - **Rule:** Reflection is not execution: confirm the response is parsed as HTML and that the value reaches an execution-capable sink before calling it XSS

- **Hypothesis:** Cookie theft via reflected XSS on an authenticated settings page
  - **Invalidated by:** The session cookie carried HttpOnly, so document.cookie returned nothing — but the script could still read the page's CSRF token and submit the password change with it, which is the real impact
  - **Rule:** Never price XSS as cookie theft until you read the cookie flags; with HttpOnly the finding is in-origin privileged action, which is usually higher impact anyway

- **Hypothesis:** Reject a report's 'steals session cookies' impact claim when the session cookie carries the HttpOnly attribute, and restate the impact as in-origin action on behalf of the victim instead.
  - **Invalidated by:** The rule is wrong if the session cookie lacks HttpOnly and document.cookie returns it to injected script, in which case full session replay IS achievable and the original impact claim stands. It is also wrong when the sensitive credential is not the cookie at all - a JWT or API token in localStorage or sessionStorage, or a CSRF token readable from the DOM, is unaffected by HttpOnly. Read the Session Management cheat sheet's own warning before assuming HttpOnly helps: it only protects the confidentiality of that one cookie.
  - **Rule:** Reject a report's 'steals session cookies' impact claim when the session cookie carries the HttpOnly attribute, and restate the impact as in-origin action on behalf of the victim instead.

- **Hypothesis:** Reject a DOM or reflected XSS candidate when the live page ships a CSP whose script-src carries a nonce or hash source without unsafe-inline and without strict-dynamic, because your injected inline script and inline event handlers cannot execute.
  - **Invalidated by:** The rule is wrong when the policy contains 'unsafe-inline' (or 'unsafe-eval' for eval-style payloads), or when strict-dynamic is present and the injection point runs on a page that already loaded a nonced/hash-trusted script - in both cases a nonce-less injected script is executed anyway and the finding is a full XSS. It is also wrong if the CSP is only a report-only header (Content-Security-Policy-Report-Only), which logs violations without blocking anything.
  - **Rule:** Reject a DOM or reflected XSS candidate when the live page ships a CSP whose script-src carries a nonce or hash source without unsafe-inline and without strict-dynamic, because your injected inline script and inline event handlers cannot execute.

- **Hypothesis:** Reject a DOM clobbering or prototype-pollution XSS candidate when the clobbered or polluted property is only read as a string into textContent, an attribute or a URL fetch, and never reaches an HTML parser or script-execution context.
  - **Invalidated by:** The rule is wrong if the clobbered or polluted property is later assigned into an HTML-executing sink - a clobbered script src/iframe src whose value navigates to attacker markup, or a polluted property consumed by a template that renders it as HTML - because that is script execution with an injection-only primitive, and it is a real XSS. OWASP's own note that CSP mitigates clobbering of script sources but not already-present code that can be abused for execution is the same distinction seen from the mitigation side.
  - **Rule:** Reject a DOM clobbering or prototype-pollution XSS candidate when the clobbered or polluted property is only read as a string into textContent, an attribute or a URL fetch, and never reaches an HTML parser or script-execution context.

- **Hypothesis:** Reject a reflected XSS candidate when the reflected value appears in the response only as HTML entities or percent/unicode escapes that the browser decodes back to inert text in that context, because encoding is what makes the reflection non-exploitable.
  - **Invalidated by:** The rule is wrong if the encoding is applied for the wrong context - for example only HTML-entity-encoded output dropped inside a JavaScript string, a URL, a CSS value or an unquoted attribute, where &quot; and &#39; do not neutralise a quote delimiter and a ';alert(1)// payload still breaks the string. It is also wrong if the entity is decoded and re-serialised anywhere before rendering (a client-side read of .innerHTML followed by a re-write, or a client-side template that re-interprets the text as HTML), because then the inert text becomes live markup.
  - **Rule:** Reject a reflected XSS candidate when the reflected value appears in the response only as HTML entities or percent/unicode escapes that the browser decodes back to inert text in that context, because encoding is what makes the reflection non-exploitable.

- **Hypothesis:** Reject a JSON API endpoint reported as XSS when the response Content-Type is application/json and no client-side code path inserts the reflected value into an HTML document.
  - **Invalidated by:** The rule is wrong if the same reflected value reaches an HTML-executing context through any code path: the API is called by a front end that assigns the response into innerHTML or a framework's raw-HTML binding, the endpoint is reachable at the same path with a text/html or JSONP callback content type, or the server renders the stored value into an HTML page for other users. Then the JSON body is only the delivery mechanism, and the finding is a genuine XSS located at the sink.
  - **Rule:** Reject a JSON API endpoint reported as XSS when the response Content-Type is application/json and no client-side code path inserts the reflected value into an HTML document.

- **Hypothesis:** Reject a prototype-pollution finding reported as XSS unless the polluted property value is read back and written into an HTML-executing sink, because polluting Object.prototype alone executes no script in any page.
  - **Invalidated by:** The rule is wrong if the polluted property is consumed by a templating engine or a client-side render that inserts it as markup - a server-side template interpolating the inherited property, or front-end code writing it to innerHTML or a raw-HTML framework binding - because then the pollution is the injection primitive and the result is stored XSS reachable by every user of the app. Equally, if the pollution reaches a code-execution gadget (a template engine option object, a child-process invocation), that is RCE, which is a stronger finding than the XSS report claimed.
  - **Rule:** Reject a prototype-pollution finding reported as XSS unless the polluted property value is read back and written into an HTML-executing sink, because polluting Object.prototype alone executes no script in any page.

- **Hypothesis:** A reflected XSS on an anonymous, read-only page is not automatically informational; it still executes script in every visitor's origin.
  - **Invalidated by:** The page's origin exposes no authenticated state, no same-origin privileged endpoints and no tokens reachable from injected script, leaving only a bare popup.
  - **Rule:** A reflected XSS on an anonymous, read-only page is not automatically informational; it still executes script in every visitor's origin.

- **Hypothesis:** Reject a sanitizer-bypass XSS claim when the rendered page shows the payload as inert text with the dangerous markup stripped, because a payload that does not become live DOM in the browser is not a bypass.
  - **Invalidated by:** The rule is wrong if a real element with a live event handler or a navigable javascript:/data: URL is present in the rendered DOM and your callback endpoint receives the request - that is a genuine sanitizer bypass and a real XSS, even if the sanitizer appeared to strip <script>. The rule also does not apply where the string is sanitized and then mutated or re-serialised before insertion, since the protection can be voided downstream; check the sink, not the sanitizer call.
  - **Rule:** Reject a sanitizer-bypass XSS claim when the rendered page shows the payload as inert text with the dangerous markup stripped, because a payload that does not become live DOM in the browser is not a bypass.

- **Hypothesis:** Reject an XSS candidate as unproven when the payload can only be made to render by pasting attacker-supplied JavaScript into the submitter's own address bar or console, because that is self-XSS and not a cross-user finding.
  - **Invalidated by:** The candidate stops being self-XSS the moment a working delivery exists: a crafted URL (or a CSRF-style auto-submitting form) that fires the payload automatically in any other user's browser, on a page an authenticated victim visits. Then it is ordinary reflected XSS and this rejection rule is wrong. Equally, if the 'pasting' step is not required because the value is stored and later rendered to other users, the finding is stored XSS, not self-XSS.
  - **Rule:** Reject an XSS candidate as unproven when the payload can only be made to render by pasting attacker-supplied JavaScript into the submitter's own address bar or console, because that is self-XSS and not a cross-user finding.

- **Hypothesis:** Reject a DOM-based XSS candidate when the traced attacker-controlled source only ever reaches textContent, innerText, or setAttribute with a hardcoded non-event attribute, because those sinks treat the value as text and never parse it as markup.
  - **Invalidated by:** The candidate is a real DOM XSS if the identical tainted value, in the identical code path, is also passed to an execution-capable sink - innerHTML/outerHTML/insertAdjacentHTML/document.write/eval/string setTimeout - anywhere the same value can reach on another page load, in a fallback branch, or for a different input shape. This rule is also wrong if setAttribute's attribute NAME is derived from the same tainted input (setAttribute(t, v) where t is user-influenced), because OWASP limits setAttribute's safety to hardcoded, innocuous attribute names; an injected name such as onmouseover re-creates an injection sink.
  - **Rule:** Reject a DOM-based XSS candidate when the traced attacker-controlled source only ever reaches textContent, innerText, or setAttribute with a hardcoded non-event attribute, because those sinks treat the value as text and never parse it as markup.

- **Hypothesis:** Reject a stored XSS candidate when the submitted payload never appears in any response served to another user or role, because a store-only write with no second-user render is not cross-site script execution.
  - **Invalidated by:** The rule is wrong if any second surface renders the stored value - an admin moderation queue, a different user's listing or profile page, a notification email, an export/CSV/PDF generator, a webhook payload or a third-party integration that re-renders the string as HTML. Any one of those makes it genuine stored XSS, because the hunter now has two distinct steps: store, then a second user's response executes it.
  - **Rule:** Reject a stored XSS candidate when the submitted payload never appears in any response served to another user or role, because a store-only write with no second-user render is not cross-site script execution.
