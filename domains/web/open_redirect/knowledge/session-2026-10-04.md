# Session debrief — 2026-10-04

What changed for `open_redirect` in this learning session, and what produced it.

## New items admitted (2, both promoted, both citing 2 independent publishers)

### 1. `open_redirect.fp_rule.a_url_that_lands_after_the_authority_is_not_a_redirect_target`
A URL whose *path/query* portion contains something authority-like (`//evil.com`,
`/\evil.com`, or a `user@host` sequence) is not an open redirect when the resolved
`Location` host is still the intended one. The authority is what the browser
uses; the rest is path.

- **Publishers:** 2 independent.
- **Operational consequence:** grepping a redirect parameter for `//` produces
  findings that do not survive a resolve. The discriminating test is the
  **resolved host after the hop**, not a substring of the parameter value.

### 2. `open_redirect.fp_rule.a_relative_or_same_origin_location_value_is_not_an_open_redirect`
A relative or same-origin `Location` value is not an open redirect. No request
leaves the origin, so an attacker cannot place their page in the chain.

- **Publishers:** 2 independent.
- **Operational consequence:** the same as above — resolve the hop.

## Why both are false-positive rules

Neither is a technique. Both exist because the corpus was accumulating reported
`open_redirect` findings that do not survive resolution, and a rule that prevents
a bad report is worth as much as a technique that finds a good one. The hunt
skill's False-positive rules section now carries both.

## Reconnaissance consequence

The class's own `fp_case` row for `open_redirect` reached the same conclusion
independently from a field observation ("`redirect-reflected-into-same-host-302-
is-not-open`"): the 302 pointed back at the same host with the parameter echoed,
so no request ever left the origin. The evidence-derived rule and the
field-derived case now say the same thing from two directions — which is the
corroboration the corpus is built to reward, arriving by a different path.
