**Report lessons**

- The folder's prior "mass assignment" note was written from an ADMIN session — it proved admin capability, not escalation. Lesson: record the role/tenant of every PoC; a PoC run as site_admin cannot support a privilege-escalation claim.
- SSRF "accepted" responses at creation time are not findings — the delivery log (`event_delivery_attempts`, `automation_logs`) is the ground truth. Two surfaces (event_targets, import_file nodes) looked vulnerable on create and were blocked at fetch; both logged `Restricted hostname or resolved IP`.
- Before claiming stored XSS from uploads, fetch the actual bytes via `?action=redirect` and check `Content-Disposition`/`Content-Type` on the signed URL — S3-served files with `attachment` disposition are not XSS.
- Webhook test endpoints reflecting upstream status codes ("Failed with status 403") are only an info signal for allowlisted URLs, not SSRF proof.

**Patterns**

- JS intelligence wins hunts — bundles/source maps leak hidden routes and undocumented APIs.
- GraphQL authenticates but fails ownership — auth ≠ authorization.
- SSRF strongest when chained — callback alone is a lead, not a finding.
- Parser differentials create real bypasses — content-type/method/header mismatches.
- Auth bugs live in recovery/fallback paths — reset, magic link, invite, MFA bypass.
- Medium signals become critical chains — compose weak signals into impact.
- Create-time vs connect-time validation gap: Files.com accepts internal URLs (169.254.169.254, 127.0.0.1) when CREATING webhook event_targets and automation import_file nodes, and only blocks at delivery (`RestrictedIpOrHostnameError`). The block is real (redirect chains, DNS-rebind names, decimal/hex IPs all stopped), but a target that validates only at creation is one refactor away from SSRF. When you see "accepted at write, blocked at fetch", verify WHICH layer blocks by reading delivery logs, not the create response.
- Unauth webhook trigger URLs (`/api/webhooks/{uuid}`) fire automations with zero auth and no observed rate limit — usable as an unauth trigger primitive on any site that has one; check for throttling explicitly.
- "Mass assignment on PATCH /users/{id}" as a lead: always test as the LOWEST-privilege role you can create, not as admin. Admin-set flags without reauth are by-design; only self/folder-admin escalation counts. Files.com gates this correctly (403 Insufficient Permission For Params; admin_group_ids accepted-but-ignored).
- Multi-tenant SaaS on wildcard subdomains (*.files.com): every host serves the CALLER's site — cross-tenant probing must use object IDs and site_id/workspace_id params, not host swapping. Host-swap sessions don't cross sites.
- Reauth gates (`X-Files-Reauthentication`) accept the account password OR a valid API key of the acting user — test both credential types when probing whether a gate can be satisfied with a weaker credential.
- API-key scoping is enforced server-side per role (user-level key got 403 on site-admin endpoints even with self-reauth) — good reference implementation to compare against.
- Login/reset error uniformity + 429 rate limiting on forgot endpoints was correct; always measure timing/error-body uniformity before calling enumeration.

Run the full suite before the change is done:

```bash
python eval/run_all.py            # every eval/test_*.py, per-file results
python eval/run_all.py --quick    # skip the slow repository-copy files
```

MEASURED 2026-10-31: this project has NO pytest suite. The tests are
standalone `eval/test_*.py` files with their own exit codes, and `run_all.py`
discovers them — so a new test file is picked up automatically and cannot be
missed by a hand-maintained list. "Run pytest" names a command that does not
exist here, which is the same failure mode as a check that cannot fail: it
reads as a verification step while verifying nothing.

Current state: **53/53 files passed** (full), **49/49** (quick).

Two checks are slow and catch defects nothing else can see:

- `eval/test_dispatch_reachability.py` — a hunt task that never reaches its
  handler. Every other suite calls a component directly, so the WIRING
  between dispatcher and handler is invisible to them by construction. This
  one spawns the real CLI against a real loopback HTTP target and asserts on
  an on-disk artifact the handler writes, so an in-process monkeypatch cannot
  make it green. MEASURED: it was FAILING (7 pass / 7 fail) while the rest of
  the suite reported green — it caught a `can_handle` that returned False for
  every key, which made hunts exit 0 and gate findings without ever dispatching
  a task.
- `eval/test_migration_lock.py` — a migration lock whose holder died still
  blocking every writer in the project.

Keep .github/workflows CI green (registry + engine checks + both of the above).

If a change breaks an existing test, fix the code or update the test
deliberately — never skip or delete tests to make them pass.
