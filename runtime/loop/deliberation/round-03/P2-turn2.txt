**1. Their wrong/overstated claim: P1 Claim 1 (PHP FastCGI null-byte injection).** The mechanism is inverted and the example is inert. The payload `../../etc/passwd.jpg` contains no NUL byte, so no truncation ever happens; and as described, both layers truncate at the same `\x00` — identical truncation yields identical views, so there is no mismatch: if the allowlist truly saw only `passwd`, it would fail and block. The real historical bug runs the opposite way: PHP's binary-safe string functions (substr, pathinfo) see the full string including the trailing `.jpg`, while the C-string filesystem call (fopen) stops at the NUL — check passes on the full view, filesystem obeys the truncated one. It was also a PHP string-handling flaw fixed in 5.3.4 (2010), not a FastCGI property.

Pending that, I downgrade to "strong resolution evidence, still not content proof."
